    Apuntes AWS Technical Essentials

    General

    AWS IAM(Identity and Access Management)

    Maneja el acceso seguro a las cuentas y recursos de AWS.

    Funcionalidades

    • Global.
    • Integrado con servicios AWS.
    • Acceso compartido a tu cuenta AWS.
    • MFA.
    • Identidad federada.
    • Uso gratuito.

    AWS root user

    • Es el usuario registrado en la cuenta AWS principal.
    • Te permite acceder a AWS Management Console.

    Best practices

    • Elegir una contraseña fuerte.
    • Habilitar autenticación multifactor para el usuario root.
    • Nunca compartir la contraseña root o las claves de acceso con nadie.
    • Deshabilitar o borrar el acceso de claves asociadas con el usuario root.
    • Crear un usuario IAM para tareas administrativas o tareas diarias.

    Access keys

    • Compuestas por access key ID y secret access key.
    • Te permiten realizar solicitudes (requests) mediante programación desde la CLI de AWS o el SDK de AWS.

    AWS Root User vs. IAM Login

    La gestión de accesos a una cuenta de AWS se divide fundamentalmente entre la identidad principal de control absoluto y las identidades delegadas de IAM.

    Diferencias en el Inicio de Sesión

    • Login como Root: Se accede a la consola de gestión introduciendo directamente la dirección de correo electrónico asociada a la cuenta y su contraseña de root.
    • Login como IAM: La interfaz solicita obligatoriamente el Account ID de 12 dígitos o el alias corporativo de la cuenta antes de requerir el nombre de usuario y la contraseña de IAM, asegurando que la autenticación se resuelva dentro del espacio de nombres de esa cuenta específica.

    Principio de Mínimo Privilegio con IAM

    Permite crear identidades acotadas (usuarios, grupos y roles) dotadas únicamente de los permisos estrictamente necesarios para desempeñar tareas operativas o de desarrollo, aislando el riesgo de seguridad frente a posibles compromisos de credenciales.

    IAM policies

    • Policy: Documento que concede o deniega permisos a los servicios y recursos de AWS.
    • Ejemplo:

    {
  "version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ec2:StartInstances",
        "ec2:StopInstances"
      ],
      "Resource": "arn:aws:ec2:*:*:instance/*"
    }
  ]
}
    - Best practice: Seguir el principio de mínimo privilegio.

    IAM groups

    • Group: Collección de usuarios IAM que heredan las politicas asignadas al grupo.
    • Los grupos de IAM pueden tener muchos usuarios, y los usuarios pueden pertenecer a muchos grupos. Pero los grupos de IAM no pueden pertenecer a otros grupos.
    • En el caso de que un usuario cambia entre diferentes roles a lo largo del día, es conveniente usar roles de IAM.
    • Best practice: Asocias políticas de IAM a grupos de IAM, en lugar de a usuarios de IAM individuales.

    IAM roles

    • Role: Identidad que puede ser asumida por una persona o un servicio para obtener acceso temporal a otros recursos o servicios de AWS.
    • Al asumir un rol de IAM, se obtienen credenciales de seguridad temporales para la sesión.
    • Los roles de IAM pueden ser utilizados por las siguientes entidades:
      • Un usuario de IAM en la misma cuenta de AWS que el rol o en una cuenta diferente.
      • Un servicio de AWS.
      • Un usuario externo autenticado por un servicio de proveedor de identidad (IdP) externo compatible con SAML 2.0 u OpenID Connect, o por un intermediario de identidad personalizado.
    • Puedes utilizar roles de IAM para conceder acceso a las identidades existentes en el directorio de usuarios de tu empresa, lo que se conoce como usuarios federados.
    • Los servicios de AWS también pueden asumir un rol de IAM para realizar acciones en su cuenta de AWS en su nombre. Al configurar un servicio de AWS, debe definir un rol —que incluya todos los permisos necesarios— para que el servicio lo asuma, siguiendo los requisitos documentados para dicho servicio.
    • Los roles asignados a un servicio de AWS son específicos de la cuenta.
    • Best practice: Los roles de IAM son ideales para situaciones en las que se debe conceder acceso a servicios o recursos de forma temporal.

    Amazon EC2

    Amazon Machine Image (AMI)

    • Al lanzar una instancia EC2, primero se especifica una Amazon Machine Image (AMI).
    • Una AMI incluye el sistema operativo, la asignación de almacenamiento, el tipo de arquitectura, los permisos de lanzamiento y cualquier aplicación de software adicional preinstalada. A continuación, la AMI se copia en el volumen del dispositivo raíz.
    • Puede utilizar una misma AMI para lanzar varias instancias EC2 con las mismas configuraciones.

    Instancias EC2

    El enfoque de AWS permite separar qué tipo (Type) de computación necesitas de cuánta (Size) necesitas. Esto te permite empezar con poco y redimensionar la instancia a medida que crece tu carga de trabajo, emparejando el hardware con el cuello de botella real y pagando solo por lo que usas.

    1. Instance Type (Tipo de instancia)

    Define la categoría de hardware de la instancia, incluyendo:

    • El balance de recursos de computación, memoria y red.
    • El tipo de procesador (Kind of processor).

    2. Instance Size (Tamaño de la instancia)

    Define qué cantidad exacta de recursos tiene asignados la instancia:

    • Núcleos de CPU virtual (vCPU).
    • Memoria del sistema (RAM).
    • Ancho de banda de red.
    • Almacenamiento de la instancia (Instance store).

    Contenedores vs Máquinas Virtuales (VMs)

    Contenedores

    • Qué es: Una unidad estandarizada que empaqueta el código de una aplicación y sus dependencias para que pueda ejecutarse en cualquier sistema operativo (OS) de forma idéntica, predecible y sin problemas de compatibilidad.
    • Ventajas frente a VMs:
      • Comparten el mismo sistema operativo y el kernel de la máquina anfitriona (host).
      • Tardan segundos en arrancar.
    • Ejemplos: Plataformas de contenedorización como el motor de Docker, una plataforma de desarrollo de software para empaquetar, desplegar y ejecutar contenedores.
    • Por lo general, las organizaciones pueden gestionar fácilmente unos pocos contenedores. A medida que se añaden más contenedores en múltiples instancias EC2 distribuidas entre zonas de disponibilidad, la gestión de los despliegues de contenedores —así como de los fallos tanto de los contenedores como de las instancias— puede volverse compleja. Para abordar esta situación, AWS ofrece servicios de orquestación de contenedores.

    Máquinas Virtuales (VMs) y Virtualización

    • Plataformas de virtualización: Utilizan un hipervisor (hypervisor).
    • Tipos de Hipervisores:
      • Type-1 (Nativo / Bare-metal): Se ejecuta directamente sobre el servidor físico (hardware) para controlarlo y gestionar los sistemas operativos invitados.
      • Type-2 (Hosted / Hospedado): Se ejecuta sobre un sistema operativo convencional.

    Servicios de Orquestación de Contenedores en AWS

    AWS ofrece dos servicios principales para gestionar y escalar contenedores:

    1. Amazon Elastic Container Service (Amazon ECS)

    • Qué es: Un sistema de gestión de contenedores altamente escalable y de alto rendimiento que permite ejecutar y escalar aplicaciones contenedorizadas.
    • Funcionamiento: Utiliza llamadas a la API para controlar aplicaciones habilitadas para Docker. Para gestionar los contenedores en las instancias EC2, requiere instalar un agente de código abierto (Amazon ECS container agent) en dichas instancias (tanto en AMIs de Linux como de Windows).

    2. Amazon Elastic Kubernetes Service (Amazon EKS)

    • Qué es: Un servicio gestionado para ejecutar y escalar aplicaciones utilizando Kubernetes (una plataforma de código abierto portable y extensible) tanto en la nube de AWS como en entornos on-premises.
    • Características: Permite crear clústeres altamente disponibles y seguros, automatizando tareas pesadas como la aplicación de parches (patching), el aprovisionamiento de nodos (node provisioning) y las actualizaciones.

    Serverless

    • Ventajas:
      • Sin servidores que aprovisionar o gestionar.
      • Se escala según el uso.
      • Solo se paga por los recursos utilizados.
      • Disponibilidad y tolerancia a fallos integradas.

    AWS Fargate

    AWS Lambda

    • Servicio de computación sin servidor (serverless) que permite ejecutar código sin aprovisionar ni gestionar servidores.
    • Solo pagas por el tiempo de computación que consumes; no hay cargos cuando el código no se está ejecutando.
    • Administración cero: Solo subes el código y AWS se encarga de todo lo necesario para ejecutarlo y escalarlo con alta disponibilidad. Se puede lanzar automáticamente desde otros servicios de AWS o llamarlo directamente desde aplicaciones web/móviles.
    • Event Source (Fuente de eventos): El origen que invoca la llamada.
    • Language Choice: Elección del lenguaje de programación.
    • Execution Environment: Permisos y recursos necesarios para la ejecución.

    Características de las Funciones Lambda

    • El código se sube como una función Lambda, la cual incluye información de configuración (nombre, descripción, punto de entrada (entry point) y requisitos de recursos). Puede empaquetar librerías (incluso nativas).
    • Diseño Stateless (Sin estado): El código debe ser apátrida; no debe asumir ninguna afinidad con la infraestructura subyacente.
      • El acceso al sistema de archivos local, procesos hijos y artefactos similares no duran más allá del tiempo de vida de la solicitud.
      • Cualquier estado persistente debe almacenarse en servicios externos como Amazon S3 o Amazon DynamoDB.

    AWS Networking

    Amazon Virtual Private Cloud (Amazon VPC)

    • Permite definir y aprovisionar una red virtual en la nube de AWS para tus recursos, similar a una red tradicional de centro de datos.
    • Al crear una VPC, se debe indicar:
      • Región
      • Nombre
      • Rango de direcciones IP (bloque CIDR primario)
    • Una VPC se extiende a lo largo de múltiples Availability Zones (AZs) en la Región seleccionada.

    Subnets (Subredes)

    • Redes más pequeñas dentro de una VPC donde se ubican los recursos de AWS. Su propósito es localizar recursos en una AZ específica y separar recursos por seguridad o rutas de acceso.
    • Alta Disponibilidad: Para garantizarla, se recomienda crear subredes públicas y privadas en al menos dos AZs diferentes.
    • Configuración de enrutamiento: Se aplica a nivel de subred para determinar si son públicas (con acceso a internet) o privadas.

    Direccionamiento CIDR (Classless Inter-Domain Routing)

    • Método para especificar rangos de IPs mediante una barra (/) y un número (ej. 192.168.1.0/24, donde los primeros 24 bits son fijos).

    Nota de AWS: AWS reserva 5 direcciones IP en cada subred (para la dirección de red, el router, el DNS, uso futuro y la dirección de broadcast). Por tanto, en una subred /24 (que da 256 IPs teóricas), quedan 251 direcciones disponibles.

    • IPs Privadas (IANA): Los bloques reservados para redes privadas son 10.x.x.x, 172.16.x.x - 172.31.x.x y 192.168.x.x. Las IPs para conectividad externa pública deben obtenerse de un registro de internet y no pertenecen a estos rangos.

    Conectividad de Red y Puertas de Enlace (Gateways)

    • Internet Gateway: Conecta tu VPC a internet de forma altamente disponible y escalable.
    • NAT Gateway: Permite que los recursos de una subred privada salgan a internet bloqueando las conexiones entrantes desde el exterior. Se debe crear un NAT gateway en cada AZ para mantener la alta disponibilidad.
    • Virtual Private Gateway: Conecta de forma encriptada tu centro de datos on-premises con la VPC (VPN). Pasos:
      1. Crear el virtual private gateway y adjuntarlo a la VPC.
      2. Crear un customer gateway conectado al data center local.
      3. Establecer la conexión VPN.
    • AWS Direct Connect: Establece una conexión física segura (cable de fibra óptica Ethernet estándar) entre el data center local y la VPC, reduciendo costes de red y aumentando el ancho de banda.

    Enrutamiento en VPC (Route Tables)

    • Las tablas de rutas controlan hacia dónde se dirige el tráfico de red.
    • Cada subred está asociada a una tabla de rutas (varias subredes pueden compartir una tabla, pero una subred no puede tener múltiples tablas).
    • Cada ruta contiene un destino (rango CIDR) y un objetivo (target) (la ruta que debe seguir).
    • Ruta local: Siempre está presente y no se puede borrar (permite tráfico entre subredes de la VPC).
    • Acceso a Internet (Público): Destino 0.0.0.0/0 (todo el tráfico restante) apuntando al ID del Internet Gateway (igw-xxxx).
    • Acceso a Internet desde Subred Privada: Requiere crear un NAT Gateway con una Elastic IP en la subred pública y actualizar la tabla de rutas de la subred privada para apuntar a dicho NAT Gateway.

    Security Groups vs. Network Access Control Lists (NACLs)

    El control de la seguridad de red en Amazon VPC se implementa mediante dos capas complementarias de filtrado que operan en diferentes niveles de la arquitectura y con distintos modelos de gestión de estado.

    Comparativa Técnica y Funcional

    Característica Security Groups Network ACLs (NACLs)
    Nivel de Operación Nivel de instancia / Interfaz de red elástica (ENI) Nivel de subred
    Gestión de Estado Stateful (Con estado) Stateless (Sin estado)
    Tipos de Reglas Solo reglas de tipo Allow (Permitir) Reglas de tipo Allow y Deny (Denegar)
    Evaluación de Reglas Se evalúan todas las reglas antes de tomar una decisión Se procesan en orden numérico secuencial estricto (de menor a mayor número)
    Configuración por Defecto Bloquea todo el tráfico entrante; permite todo el tráfico saliente La NACL predeterminada permite todo el tráfico de entrada y salida
    NACL Personalizada N/A Bloquea todo el tráfico de entrada y salida hasta añadir reglas explícitas

    Comportamiento Stateful vs. Stateless

    Comportamiento con Estado (Stateful) en Security Groups
    • Si se permite una petición entrante mediante una regla Inbound, el tráfico de respuesta saliente se permite automáticamente sin necesidad de configurar una regla Outbound equivalente.
    • Si se autoriza una conexión saliente mediante una regla Outbound, la respuesta entrante asociada se permite automáticamente sin requerir reglas Inbound.
    Comportamiento sin Estado (Stateless) en Network ACLs
    • No existe seguimiento de sesiones ni memoria de conexiones activas.
    • Cada paquete de red se evalúa de forma independiente en ambas direcciones: para que una comunicación sea exitosa, debe existir una regla explícita en la tabla Inbound para el tráfico entrante y una regla explícita en la tabla Outbound para el tráfico de respuesta saliente.

    1. FLUJO STATEFUL (SECURITY GROUPS - Nivel de Instancia) 

    [ Instancia A (Cliente) ]          [ Instancia B (Servidor Web) ]
 Security Group A (SG-A)               Security Group B (SG-B)
     |                                       |
     |--- Petición HTTPS  ------------------>|  (SG-B: Requiere Inbound 443)
     |    (Destino: Puerto 443)              |
     |    (SG-A: Requiere Outbound 443)      |
     |                                       |
     |<-- Respuesta HTTPS  ------------------|  (SG-B: NO requiere Outbound)
          (Automática por Stateful)
          (SG-A: NO requiere Inbound)
    2. FLUJO STATELESS (NETWORK ACLs - Nivel de Subred) 
      [ Subred Cliente ]                [ Subred Servidor ]
   NACL Subred Cliente               NACL Subred Servidor
       |                                 |
       |--- Petición HTTPS  ------------>|  (NACL Servidor: Inbound 443)
       |    (Puerto Destino: 443)        |
       |    (NACL Cliente: Outbound 443) |
       |                                 |
       |<-- Respuesta HTTPS  ------------|  (NACL Servidor: Outbound 1024-65535)
            (Hacia Puerto Efímero)
            (NACL Cliente: Inbound 1024-65535)

    Gestión de Puertos Efímeros (Ephemeral Ports) en NACLs

    Cuando un cliente establece una conexión saliente hacia un servicio externo (ej. peticiones HTTPS al puerto 443), el sistema operativo del cliente selecciona dinámicamente un puerto de origen denominado puerto efímero, ubicado dentro del rango 1024 - 65535.

    Reglas Requeridas en Arquitecturas con NACLs Personalizadas
    • Subred del Cliente (Petición Saliente):
      • Regla Outbound: Permitir tráfico hacia la IP de destino en el puerto de servicio (TCP 443).
      • Regla Inbound: Permitir tráfico de retorno desde la IP del servidor en el rango de puertos efímeros (TCP 1024-65535).
    • Subred del Servidor (Recepción de Tráfico):
      • Regla Inbound: Permitir tráfico entrante en el puerto de escucha (TCP 443) desde el origen correspondiente.
      • Regla Outbound: Permitir tráfico de respuesta saliente hacia el rango de puertos efímeros (TCP 1024-65535) del cliente.

    Capas de Seguridad en Profundidad (Defense in Depth)

    • Nivel de Subred (NACLs): Actúa como firewall perimetral de la subred para filtrar o bloquear rangos CIDR completos o IPs específicas mediante reglas de denegación explícita (Deny).

    • Nivel de Instancia (Security Groups): Actúa como firewall virtual a nivel de interfaz de red (ENI) para permitir tráfico granular entre recursos específicos o grupos de seguridad referenciados.

    • Nivel de Sistema Operativo (Host-Based Firewalls): Firewalls internos del sistema operativo (como Windows Defender Firewall o iptables/nftables en Linux) que aplican filtrado a nivel de proceso o inspección adicional de paquetes en el host.

    AWS Storage

    • Tipos de almacenamiento:
    • Block storage.
    • File storage.
    • Object storage.

    Block Storage (Almacenamiento en Bloques)

    • Funcionamiento: Los datos se almacenan en dispositivos divididos en bloques de tamaño fijo (ej. 512 bytes). Las aplicaciones y sistemas de archivos regulan cómo se acceden, combinan y modifican.
    • Servicios principales en AWS:
      • Amazon EC2 Instance Store: Almacenamiento temporal a nivel de bloque ubicado en el mismo servidor físico que hospeda la instancia EC2. Los datos se pierden al detener o terminar la instancia.
      • Amazon EBS (Elastic Block Store): Almacenamiento desacoplable asociado a una Availability Zone (como un disco duro externo). Los datos se conservan aunque detengas o termines la instancia, permitiendo desconectar el volumen y reasignarlo a otra máquina.
    • Características clave de EBS:
      • Snapshots: Copias de seguridad completas e incrementales que permiten respaldar volúmenes a otra AZ o usarlas en nuevas instancias.
      • Multi-Attach: Permite adjuntar un solo volumen Provisioned IOPS SSD (io1 o io2) a múltiples instancias dentro de la misma AZ, ideal para aplicaciones Linux en clúster con escrituras concurrentes.
      • Tipos de volúmenes:
        • SSD: Para cargas de trabajo aleatorias moderadas/medias y reemplazo de SAN de alto rendimiento.
        • HDD: Para cargas muy modestas o de streaming de alto rendimiento (no aptos como discos de arranque).

    File Storage (Almacenamiento de Archivos)

    • Funcionamiento: Permite a usuarios, aplicaciones y servicios acceder a los datos mediante un sistema de archivos compartido (similar a una unidad de red centralizada).
    • Servicios principales en AWS:
      • Amazon EFS (Elastic File System): Sistema de archivos escalable compatible con servicios Cloud y recursos on-premises (estos últimos a través de AWS Direct Connect). Soporta miles de conexiones simultáneas desde instancias EC2 en múltiples AZs usando el protocolo estándar NFSv4.
      • Amazon FSx for Windows File Servers: Almacenamiento de archivos totalmente gestionado accesible mediante el protocolo estándar SMB. Ofrece opciones de despliegue Single-AZ/Multi-AZ, integración con Active Directory, backups gestionados y soporte para discos HDD y SSD.

    Object Storage (Almacenamiento de Objetos)

    • Funcionamiento: Los archivos se almacenan como objetos. Cada objeto consta de datos, metadatos (tamaño, propósito, fecha de modificación, etc.) y una clave de objeto (object key, que actúa como identificador único).
    • Diferencia clave con bloques: Al actualizar un archivo, se actualiza el objeto completo, no partes individuales de este.
    • Amazon S3 (Simple Storage Service):
      • Servicio de almacenamiento a nivel de objeto altamente escalable (almacenamiento ilimitado). El tamaño máximo por archivo es de 5 TB.
      • Los objetos se guardan dentro de S3 Buckets (similares a carpetas). El nombre del bucket debe ser único a nivel global, aunque se cree dentro de una Región específica.
      • Identificador único: Se compone de Nombre de Bucket + Key + Version ID.
      • Seguridad por defecto: Los buckets son privados por defecto y S3 Block Public Access viene habilitado de serie. Se gestiona el acceso mediante IAM Policies, Bucket Policies (máx 20 KB) y ACLs. Los datos se pueden cifrar en tránsito (SSL/TLS) y en reposo (Server-side encryption o Client-side encryption).

    Clases de Almacenamiento de Amazon S3 (S3 Storage Classes)

    Amazon S3 ofrece distintas clases de almacenamiento diseñadas para optimizar costes según la frecuencia de acceso, los tiempos de recuperación requeridos y la resiliencia geográfica.

    • S3 Standard: Clase predeterminada para datos de acceso frecuente y propósito general; distribuida en al menos 3 Zonas de Disponibilidad (AZs).
    • S3 Intelligent-Tiering: Optimiza costes monitorizando patrones de acceso y moviendo automáticamente los objetos entre niveles sin impacto en el rendimiento ni tarifas de recuperación.
    • S3 Standard-IA (Infrequent Access): Para datos a los que se accede con poca frecuencia pero que exigen disponibilidad inmediata en milisegundos (mínimo 3 AZs; menor coste por GB con tarifa por GB recuperado).
    • S3 One Zone-IA: Para datos poco frecuentes y fácilmente reproducibles; se almacenan en una única AZ para reducir costes un 20% respecto a Standard-IA.
    • S3 Glacier Instant Retrieval: Almacenamiento de archivo para datos de acceso trimestral o semestral que requieren entrega inmediata en milisegundos.
    • S3 Glacier Flexible Retrieval: Archivo clásico con tiempos de recuperación configurables de minutos a horas (no apto para acceso en tiempo real).
    • S3 Glacier Deep Archive: Archivo seguro de ultra bajo coste para retención a largo plazo (7-10 años) con tiempos de recuperación de 12 a 48 horas.

    Modos de Recuperación en la Familia S3 Glacier

    Para las clases de archivo no instantáneas, AWS ofrece diferentes velocidades de extracción (Retrieval Tiers):

    • S3 Glacier Flexible Retrieval:
      • Expedited: Recuperación urgente en 1 a 5 minutos (mayor coste por GB recuperado).
      • Standard: Recuperación estándar en 3 a 5 horas.
      • Bulk: Recuperación masiva económica en 5 a 12 horas.
    • S3 Glacier Deep Archive:
      • Standard: Recuperación estándar en 12 horas.
      • Bulk: Recuperación masiva económica en 48 horas.

    Reglas de Ciclo de Vida y Transición (S3 Lifecycle Policies)

    Permiten automatizar la reducción de costes de almacenamiento moviendo objetos entre clases o programando su eliminación definitiva:

    • Acciones de Transición (Transition Actions): Definen cuándo los objetos deben migrar a una clase de almacenamiento más económica.
      • Flujo en cascada típico: S3 Standard \(\rightarrow\) Día 30 a S3 Standard-IA \(\rightarrow\) Día 90 a S3 Glacier Flexible Retrieval o Glacier Deep Archive \(\rightarrow\) Día 365: Eliminación (Expiration).
    • Acciones de Expiración (Expiration Actions): Definen cuándo se eliminan permanentemente los objetos o caducan los marcadores de eliminación (Delete Markers) huérfanos.
    • Gestión de Versiones Anteriores (Noncurrent Versions): En buckets con versionado activado, permite configurar reglas independientes (NoncurrentVersionTransition y NoncurrentVersionExpiration) para mover o borrar versiones obsoletas de objetos sin alterar la versión actual.

    Trampas y Patrones Clave para Certificación (DVA-C02 & DOP-C02)

    • Criterio de Decisión para S3 Intelligent-Tiering: Si el escenario menciona patrones de acceso impredecibles, desconocidos o estacionales y exige optimizar costes sin riesgo operativo ni tarifas por recuperación de datos por GB, la respuesta correcta es S3 Intelligent-Tiering.
    • Riesgo de Pérdida de Datos en S3 One Zone-IA: Al almacenar los datos en una única Zona de Disponibilidad, la pérdida o desastre físico en esa AZ provoca la destrucción permanente de los datos. Nunca debe seleccionarse para datos irremplazables o sin respaldo externo.
    • Sobrecostes por Tamaño Mínimo Facturable: Las clases IA, Glacier Instant, Glacier Flexible y Glacier Deep Archive aplican una facturación mínima de 128 KB por objeto. Si una aplicación almacena millones de archivos pequeños (ej. archivos JSON o logs de 5 KB), moverlos a Glacier o Standard-IA incrementará la factura total debido al redondeo a 128 KB y a las tarifas de solicitud de API (PUT/LIST/Lifecycle transition requests).
    • Penalización por Eliminación Temprana (Early Deletion Fee): Borrar, sobrescribir o transicionar un objeto antes de su límite mínimo de retención (30 días en IA, 90 días en Glacier Flexible/Instant, 180 días en Deep Archive) genera el cobro del prorrateo completo de los días restantes como si hubiera permanecido almacenado.

    Control de Versiones en S3 (Versioning)

    • Se habilita a nivel de bucket (por defecto viene deshabilitado).
    • Conserva múltiples versiones de un objeto en el mismo bucket, protegiéndolo de borrados accidentales y sobrescrituras.
    • MFA Delete: Capacidad de seguridad adicional que exige autenticación multifactor para borrar permanentemente una versión o cambiar el estado de versionado del bucket.
    • Comportamiento de Borrado (Delete Markers):
      • Una solicitud simple de DELETE sobre un objeto versionado no elimina los datos; inserta un Delete Marker que pasa a ser la versión actual.
      • Si se solicita un GET sin especificar versionId, S3 devuelve un error 404 Not Found.
      • Para eliminar permanentemente un objeto, se debe enviar una solicitud de borrado especificando de forma explícita el versionId.
    • Estados de Versionado de un Bucket:
      • Unversioned (por defecto): Sin versionado activo; los objetos no tienen identificador de versión.
      • Versioning-enabled: Todos los objetos nuevos y modificaciones reciben un Version ID único generado por S3.
      • Versioning-suspended: Una vez activado, el versionado no se puede desactivar, solo suspender. Los objetos nuevos obtienen Version ID: null y se conservan intactas todas las versiones previas existentes.

    Bases de Datos en AWS

    Beneficios generales de las bases de datos en la nube

    • Purpose-built (Específicas para cada propósito): AWS soporta más de 15 motores de bases de datos especializados (relacionales, clave-valor, documentos, etc.) para construir aplicaciones altamente escalables.
    • Performance at scale (Rendimiento a escala): Bases de datos hasta 3-5 veces más rápidas que alternativas populares, o NoSQL con latencias de microsegundos o submilisegundos (ej. Amazon Aurora ofrece 5 veces el rendimiento de MySQL estándar y 3 veces el de PostgreSQL).
    • Fully managed (Totalmente gestionadas): AWS se encarga de tareas como aprovisionamiento, parches, configuración y backups.
    • Secure and highly available: Alta disponibilidad, fiabilidad y seguridad con soporte multi-región y cifrado de extremo a extremo.

    Tipos de Bases de Datos y Servicios AWS

    • Relational (Relacionales): Tablas con filas y columnas (estructuras predefinidas). Aplicaciones ERP, CRM, ecommerce.
      • Servicios: Amazon Aurora, Amazon RDS, Amazon Redshift.
    • Key-value (Clave-valor): Optimizadas para lectura/escritura de grandes volúmenes. Webs de alto tráfico, ecommerce, gaming.
      • Servicios: Amazon DynamoDB.
    • In-memory (En memoria): Para acceso en tiempo real. Caché, gestión de sesiones, tablas de clasificación (leaderboards).
      • Servicios: Amazon ElastiCache (Memcached, Redis), Amazon MemoryDB.
    • Document (Documentales): Datos semi-estructurados en formato JSON. Gestión de contenido, catálogos, perfiles de usuario.
      • Servicios: Amazon DocumentDB.
    • Wide column (Columnas anchas): NoSQL para aplicaciones industriales a gran escala. Mantenimiento de equipos, flotas.
      • Servicios: Amazon Keyspaces.
    • Graph (Grafos): Consultas de millones de millones de relaciones altamente conectadas. Detección de fraudes, redes sociales, motores de recomendación.
      • Servicios: Amazon Neptune.
    • Time series (Series temporales): Datos que cambian con el tiempo. IoT, DevOps, telemetría industrial.
      • Servicios: Amazon Timestream.
    • Ledger (De libros mayores): Registros inmutables y criptográficamente verificables de transacciones. Cadenas de suministro, transacciones bancarias.
      • Servicios: Amazon QLDB (Quantum Ledger Database).

    Bases de Datos Relacionales (Conceptos y RDS)

    • Estructura: Organizadas en tablas (filas como registros, columnas como atributos).
      • Primary Key (Clave primaria): Identificador único de cada fila.
      • Foreign Key (Clave foránea): Referencia a la clave primaria de otra tabla para evitar redundancias.
    • SQL y el Principio ACID: Utilizan SQL para consultar y unir (join) tablas. Son estrictamente exactas adhiriéndose al principio ACID (Atomicidad, Consistencia, Aislamiento y Durabilidad).

    Responsabilidades: On-Premises vs EC2 vs Managed (RDS/Aurora)

    • On-Premises: El cliente lo gestiona absolutamente todo (desde la app hasta la sala de servidores, hardware, OS y parches).
    • EC2 (Self-managed): Responsabilidad compartida. El cliente gestiona la optimización, escalado, backups, parches de software y del SO. AWS se encarga de la instalación física del SO, mantenimiento de servidores, rack and stack, energía y red.
    • Managed (Amazon RDS): El cliente solo optimiza la aplicación. AWS se encarga de todo lo demás (escalado, alta disponibilidad, backups, parches, SO, hardware y centro de datos).

    Amazon RDS (Relational Database Service)

    • Servicio web gestionado para crear bases de datos relacionales seguras y escalables (soporta PostgreSQL, MySQL, MariaDB, Oracle, SQL Server y Aurora). No permite acceso directo al host subyacente.
    • DB Instance Classes (Capacidad):
      • Standard: Propósito general (ej. db.m6g, db.m5).
      • Memory Optimized: Aplicaciones intensivas en memoria (ej. db.r6g, db.r5).
      • Burstable Performance: Rendimiento base con capacidad de pico en CPU (ej. db.t4g, db.t3).
    • Almacenamiento (DB Instance Storage): Utiliza volúmenes de Amazon EBS (General Purpose SSD, Provisioned IOPS para baja latencia/alto I/O, y Magnetic para compatibilidad heredada).
    • Seguridad: Se despliegan dentro de una subred privada en una VPC. Se recomienda usar IAM con permisos mínimos, habilitar cifrado en reposo y rotar credenciales.
    • Backups:
      • Automáticos: Activados por defecto. Respaldan la BD y logs de transacciones creando snapshots del volumen. Retención configurable hasta 35 días.
      • Database Snapshots: Copias manuales almacenadas en Amazon S3 que se conservan hasta que se borren explícitamente.
    • Redundancia (Multi-AZ): Crea una copia secundaria de la base de datos en otra AZ en modo standby. Si la primaria falla, RDS conmuta automáticamente a la secundaria (failover).

    Amazon DynamoDB (NoSQL Key-Value)

    • Qué es: Base de datos NoSQL totalmente gestionada y serverless. Ofrece rendimiento rápido y predecible con escalabilidad fluida. Los datos se guardan en SSDs y se replican automáticamente entre múltiples AZs.
    • Componentes Principales:
      • Tables (Tablas): Colecciones de datos.
      • Items (Elementos): Grupo de atributos unívocamente identificables dentro de una tabla (cantidad ilimitada).
      • Attributes (Atributos): Elementos de datos fundamentales.
    • Claves (Keys):
      • Partition Key: Obligatoria. Determina la partición física de almacenamiento para distribuir la carga.
      • Composite Primary Key (Clave primaria compuesta): Se compone de una Partition Key y una Sort Key cuando la clave de partición sola no es única.

    Monitorización, Escalado y Balanceo de Carga en AWS

    Monitorización

    Amazon CloudWatch (Monitorización y Observabilidad)

    • Qué es: Servicio para monitorizar recursos y la infraestructura (tanto en AWS como on-premises) en tiempo real o casi real, recopilando métricas, logs y alarmas en un solo lugar.
    • Conceptos de Métricas:
      • Namespaces (Espacios de nombres): Contenedores que aíslan métricas entre sí (ej. AWS/EC2).
      • Dimensions (Dimensiones): Pares de clave/valor asociados a una métrica para filtrar resultados (ej. filtrar por un InstanceId específico).
      • Custom Metrics / High-Resolution: Permite publicar métricas propias con granularidad de hasta 1 segundo.
    • CloudWatch Dashboards: Páginas personalizadas con widgets (gráficos, tablas) para visualizar métricas, pudiendo combinar datos de diferentes regiones en una vista global.
    • CloudWatch Alarms: Automatizan acciones basadas en cambios de estado de una métrica al superar un umbral durante un tiempo determinado.
      • Estados posibles: OK (dentro del umbral), ALARM (fuera del umbral) y INSUFFICIENT_DATA (datos insuficientes o no disponibles).
      • Acciones: Pueden activar cambios en EC2, políticas de Auto Scaling o notificaciones.

    Escalabilidad

    Estrategias de Escalado (Vertical vs Horizontal)

    • Vertical Scaling (Escalado Vertical): Cambiar la capacidad de una instancia (CPU, memoria, disco) seleccionando un tipo o familia de instancia diferente.
      • Proceso manual: 1. Detener instancia \(\rightarrow\) 2. Modificar tamaño/tipo \(\rightarrow\) 3. Iniciar instancia.
    • Horizontal Scaling (Escalado Horizontal): Añadir o eliminar instancias EC2 según la demanda de tráfico. Es un proceso automatizado e ilimitado mediante Amazon EC2 Auto Scaling.

    Amazon EC2 Auto Scaling

    • Propósito: Aumenta la disponibilidad de la aplicación y reduce costes añadiendo/quitando instancias automáticamente y manteniendo la salud de la flota (fleet management). Si una instancia falla, la termina y la reemplaza por una nueva de forma automática.
    • Launch Template (Plantilla de Lanzamiento): Almacena los parámetros de configuración (AMI, tipo de instancia, security groups, volúmenes) para reutilizarlos al lanzar nuevas instancias. Soporta versiones para facilitar rollbacks.
    • Auto Scaling Group (ASG): Define dónde se despliegan los recursos (requiere especificar al menos dos subredes en diferentes AZs). Se controla mediante tres ajustes de capacidad:
      • Minimum: Número mínimo garantizado de instancias ejecutándose.
      • Maximum: Límite máximo al que puede escalar horizontalmente.
      • Desired capacity: Capacidad deseada actual (debe estar entre el mínimo y el máximo).
    • Características principales: Escalado automático (in/out), integración con CloudWatch, Fleet Management, Predictive Scaling (machine learning para detectar patrones) y soporte para múltiples modelos de compra (On-Demand y Spot).

    Balanceo de Carga

    Elastic Load Balancing (ELB)

    • Qué es: Servicio altamente disponible y escalable que distribuye automáticamente el tráfico entrante de la aplicación entre múltiples destinos (instancias EC2, contenedores, direcciones IP, funciones Lambda) en una o varias AZs.
    • Health Checks: Mecanismo mediante códigos de respuesta API (ej. 200 OK o 503 Unavailable) para comprobar si un destino está operativo. Si falla, el ELB redirige el tráfico a los recursos sanos.
    • Componentes: Listeners (oyentes), Target groups (grupos de destino) y Rules (reglas).
    Tipos principales de Load Balancers:
    • Application Load Balancer (ALB):
      • Ideal para tráfico HTTP y HTTPS.
      • Opera a nivel de petición (Capa 7).
      • Características: Seguridad avanzada, deslastre TLS (TLS offloading), Sticky sessions (cookies de sesión), redirecciones automáticas (HTTP a HTTPS), respuestas fijas y enrutamiento basado en contenido (según cabeceras, rutas URL, métodos HTTP o IP de origen).
    • Network Load Balancer (NLB):
      • Ideal para tráfico TCP y UDP.
      • Opera a nivel de conexión (Capa 4).
      • Características: Latencia ultra baja, persistencia de sesiones (sticky sessions a nivel de target group), conservación de la IP de origen del cliente, soporte para IP estática y Elastic IPs por AZ, y DNS failover automático mediante Route 53.
