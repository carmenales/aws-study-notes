    Elementos Kubernetes

    Control plane

    • Es la capa de gestión de Kubernetes.
    • El control plane decide el estado deseado y el data plane lo ejecuta realmente sobre infraestructura física o virtual.
    • Está formado por los componentes que gestionan la API, el estado, la programación y el control del clúster.
    etcd
    • Base de datos distribuida y confiable que guarda el estado del clúster.
    • Contiene la configuración y el estado de todos los recursos de Kubernetes.
    • La integridad de etcd es crítica para la gestión del cluster.
    api-server
    • Es el punto de entrada principal a Kubernetes.
    • Toda operación (crear, leer, actualizar, borrar) pasa por el API Server.
    • Expone la API REST del clúster y valida las peticiones.
    controller manager
    • Es el componente encargado de gestionar el estado deseado del sistema.
    • Asegura que los recursos del clúster permanezcan en el estado correcto.
    • Controla aspectos como replicas, nodos y endpoints.
    scheduler
    • Es el componente del control plane que decide en qué nodo se debe ejecutar cada pod.
    • Tiene en cuenta restricciones como recursos disponibles, afinidad, taints y tolerations.
    • El objetivo es equilibrar el uso de recursos y cumplir los requisitos de programación.

    Data plane

    • Es la capa donde se ejecutan las cargas de trabajo.
    • Incluye los nodos worker que ejecutan los contenedores y los agentes de Kubernetes.
    • Aquí se ejecutan los pods y se gestionan los contenedores reales.
    Nodes
    • Un nodo es una máquina física o virtual que ejecuta contenedores.
    • Cada nodo tiene un sistema operativo, un runtime de contenedores y componentes de Kubernetes.
    • Los nodos pueden estar en Linux o Windows según la carga de trabajo.
    kubelet
    • Agente que se ejecuta en cada nodo worker.
    • Se comunica con el control plane y garantiza que los contenedores definidos en los pods estén corriendo correctamente.
    • Es responsable de registrar el nodo y reportar su estado.
    kube-proxy
    • Mantiene las reglas de red de los servicios y conexiones de red dentro del clúster.
    • Permite que los pods puedan comunicarse entre sí y con servicios externos según la red del clúster.
    • Actúa como proxy de red para cada nodo.

    Pods

    • Un pod es la unidad mínima de despliegue en Kubernetes.
    • Un pod puede contener uno o varios contenedores que comparten red, almacenamiento y configuración.
    • Normalmente cada pod ejecuta una sola aplicación principal y, si hace falta, contenedores auxiliares.
    • Los pods son efímeros: pueden reiniciarse, moverarse o recrearse; por eso no se debe guardar estado dentro del pod.

    Workloads

    • Son los recursos que gestionan la ejecución de aplicaciones.
    • Deployment: asegura que un número determinado de réplicas de un pod se estén ejecutando. Maneja actualizaciones y rollback.
    • ReplicaSet: mantiene la cantidad deseada de réplicas de un pod.
    • StatefulSet: para aplicaciones con estado, orden y identidad estables, como bases de datos o sistemas con persistencia.
    • DaemonSet: garantiza que un pod se ejecute en cada nodo o en un subconjunto de nodos; se usa para agentes, métricas o seguridad.
    • Job: ejecuta una tarea puntual y termina cuando finaliza.
    • CronJob: ejecuta jobs según una programación tipo cron.

    Services

    • Un Service es una abstracción que expone un conjunto de pods como un punto de acceso estable.
    • Permite la comunicación con una aplicación sin depender de las IPs de los pods individuales.
    • Tipos principales:
      • ClusterIP: acceso interno dentro del clúster.
      • NodePort: expone el servicio en un puerto del nodo.
      • LoadBalancer: crea un balanceador externo para acceder a la aplicación.
    • Los Services resuelven la conectividad entre microservicios y clientes.

    Deployments

    • Un Deployment define el estado deseado de una aplicación y gestiona la creación y actualización de pods.
    • Permite realizar actualizaciones declarativas y revertir cambios fácilmente.
    • Aplica estrategias de despliegue como rolling update y recreate.
    • Es la forma más común de desplegar aplicaciones en Kubernetes.

    Namespaces

    • Son espacios lógicos dentro de un clúster para aislar recursos.
    • Se usan para separar entornos como desarrollo, pruebas y producción.
    • Ejemplos: default, kube-system, kube-public.
    • También permiten aisolar equipos o proyectos dentro del mismo clúster.

    ConfigMaps y Secrets

    • Ambos se usan para separar configuración y credenciales del código de la aplicación.
    • Ayudan a mantener los contenedores más seguros y reutilizables.
    • ConfigMap: almacena configuración no sensible como variables de entorno o archivos de configuración.
    • Secret: almacena información sensible como contraseñas, tokens y claves privadas.

    Volumes

    • Un volume es un mecanismo para persistir datos o compartir almacenamiento entre contenedores dentro de un pod.
    • Los datos de un contenedor no son persistentes por defecto; los volumes permiten conservar información.
    • Se usan para configuraciones, logs, bases de datos temporales y archivos compartidos.

    Afinidad de los nodos

    • Sirve para optimizar disponibilidad, rendimiento y colocación de cargas de trabajo.
    • Node affinity: permite dirigir un pod a nodos con determinadas etiquetas o características.
    • Anti-affinity: evita que dos pods se ejecuten en el mismo nodo si es necesario.

    Por ejemplo, un pod puede ejecutarse solo en nodos con GPU o en nodos de tipo de producción.

    Plugins Kubernetes

    Helm

    • Helm es un gestor de paquetes para Kubernetes.
    • Los paquetes se llaman charts y contienen plantillas, valores y dependencias para desplegar aplicaciones.
    • Facilita la automatización de despliegues complejos con variables y reutilización.
    • Se usa mucho para instalar servicios como Prometheus, Nginx Ingress, ArgoCD y bases de datos.
    • Helm charts: empaquetan una aplicación o servicio con sus manifiestos y configuración, permitiendo desplegarlo de forma reproducible y versionada.
    Objetivo de Helm

    Kubernetes puede desplegar aplicaciones con muchos archivos YAML, pero pronto se vuelve difícil de mantener cuando hay:

    • Varios servicios.
    • Muchas variables de entorno.
    • Distintos entornos (dev, test, prod).
    • Configuraciones distintas por entorno.
    • Versiones y rollbacks frecuentes.

    Helm resuelve eso con un concepto simple:

    Un chart es un paquete que contiene la aplicación o servicio incluye sus manifiestos de Kubernetes, variables, plantillas y dependencias permite desplegarlo igual en distintos entornos, solo cambiando valores.

    En resumen, el objetivo de Helm es:

    • Automatizar despliegues.
    • Reutilizar configuraciones.
    • Versionar aplicaciones.
    • Facilitar la actualización y rollback.
    • Evitar repetir manualmente los mismos YAMLs.
    ¿Qué aporta realmente?
    • Reproducibilidad.
    • Parametrización.
    • Trazabilidad de versiones.
    • Despliegues más ordenados.
    • Menos errores manuales.
    Resumen

    Helm es una herramienta para empaquetar, versionar y desplegar aplicaciones en Kubernetes con plantillas reutilizables y configuración parametrizada.

    ArgoCD

    • ArgoCD es una herramienta de despliegue GitOps para Kubernetes.
    • Mantiene el estado del clúster sincronizado con el repositorio Git.
    • Permite ver diferencias entre el estado deseado en Git y el estado real en el clúster.
    • Es útil para despliegues repetibles, auditoría y automatización de entregas.

    Cluster

    • Un clúster de Kubernetes es un conjunto de nodos gestionados por un control plane.
    • Agrupa recursos y workloads que colaboran para ejecutar aplicaciones distribuidas.
    • Un clúster puede abarcar varias zonas de disponibilidad y múltiples nodos.

    Amazon EKS

    • Amazon Elastic Kubernetes Service (Amazon EKS) es un servicio totalmente gestionado para ejecutar Kubernetes en AWS.
    • AWS se encarga de la parte control plane en Amazon EKS, incluyendo la API, el almacenamiento del estado y los componentes de control.
    • El control plane de EKS está gestionado por AWS y se encarga de tareas complejas como actualizaciones, patches, alta disponibilidad y seguridad.
    • Los usuarios solo gestionan los nodos, las cargas de trabajo y la configuración del clúster.
    • EKS se integra con Amazon VPC, IAM, Amazon ECR y otros servicios de AWS.
    • Permite desplegar aplicaciones empresariales, microservicios y servicios distribuidos en Kubernetes.
    • Modelos:
      • Managed node groups: AWS gestiona la infraestructura de los nodos EC2.
      • Self-managed nodes: el usuario crea y administra los nodos.
      • Fargate: para nodos serverless sin gestionar infraestructura.
    • EKS ofrece alta disponibilidad al desplegar el control plane en varias zonas de disponibilidad.
    • Es ideal para migrar aplicaciones Kubernetes desde on-premises o para nuevas arquitecturas cloud-native.
    • Modo ahorro: todos los workloads que no sean fundamentales se apagan.
      • kube-downscaler: plugin para apagar cargas de trabajo que no sean esenciales durante horas o periodos de baja actividad.

    Node Group

    • Un node group es un conjunto de nodos de Kubernetes gestionados por EKS.
    • Puede estar basado en EC2 con Amazon Linux o Windows, y se administra como una unidad.
    • EKS soporta node groups gestionados y auto-scaling para ajustar la capacidad de los nodos.
    • Los node groups permiten aislar diferentes tipos de cargas de trabajo por perfil de capacidad.

    Auto Scaling Group

    • Es un conjunto de instancias EC2 con capacidad de escalado automática.
    • En EKS, se usa para crear grupos de nodos que aumentan o disminuyen según la demanda.
    • Facilita la escalabilidad horizontal de los nodos del clúster.
    • Puede ampliar o reducir los nodos según métricas de CPU, memoria o métricas personalizadas.

    Amazon ECR

    • Amazon Elastic Container Registry (Amazon ECR) es el registro privado de contenedores de AWS.
    • Permite almacenar imágenes Docker para usarlas en ECS, EKS y otros servicios.
    • Integra perfectamente con IAM y con pipelines de CI/CD.
    • Soporta control de versiones de imágenes, seguridad y políticas de ciclo de vida.
    • Es la opción natural para albergar imágenes usadas por clústeres EKS.

    Amazon Inspector

    • Amazon Inspector es un servicio de escaneo de seguridad para evaluar vulnerabilidades en aplicaciones y contenedores.
    • En entornos de contenedores puede detectar riesgos en imágenes, paquetes y configuraciones.
    • Emite eventos a Amazon EventBridge para integrar alertas y automatización.
    • Ayuda a detectar problemas de seguridad antes de desplegar a producción.
    • Es una parte importante del cumplimiento y de la gobernanza de seguridad dentro de EKS.

    AWS Fargate

    • AWS Fargate es un motor de computación serverless para contenedores.
    • Permite ejecutar pods de Kubernetes sin aprovisionar ni gestionar nodos EC2.
    • Se paga por los recursos consumidos por cada pod.
    • Es útil para cargas de trabajo con patrones irregulares o que requieren menos operación.
    • Reduce la complejidad operativa porque AWS gestiona el host y la infraestructura.
    • Fargate profiles: conjunto de reglas que indican qué pods deben ejecutarse en Fargate.
    • En EKS, un Fargate profile suele definir:
      • namespace en el que se ejecutan los pods
      • labels para seleccionar los workloads
      • la configuración del pod que debe lanzarse en Fargate
    • Ventajas:
      • No se gestionan instancias EC2.
      • Escala automáticamente.
      • Mejor para workloads con pico de uso.
      • Alineado con el modelo serverless.
    • Limitaciones:
      • Menos control sobre el host y la configuración del sistema operativo.
      • Se debe ajustar bien el tamaño de la demanda para evitar coste innecesario.

    Amazon EC2

    • Amazon EC2 ofrece instancias virtualizadas en la nube para ejecutar aplicaciones.
    • En EKS, los nodos worker suelen ejecutarse sobre instancias EC2.
    • Las instancias EC2 permiten más control sobre el sistema operativo, la red, el almacenamiento y el rendimiento.
    • Se pueden elegir tipos de instancia según la necesidad de CPU, memoria, red y almacenamiento.
    • EC2 es útil cuando se necesita:
      • personalización del entorno
      • control avanzado del sistema operativo
      • cargas de trabajo con requisitos específicos
      • integración con grupos de autoescalado y node groups

    En comparación con Fargate, EC2 requiere más operación pero ofrece mayor flexibilidad y personalización.

    Seguridad

    Seguridad en Kubernetes

    • La seguridad en Kubernetes se basa en controlar quién puede acceder al clúster, qué puede hacer y cómo se comunican los recursos.
    • Hay que proteger el control plane, los nodos, las redes y los secretos.
    • El principio básico es el de mínimo privilegio: dar solo los permisos necesarios.

    Autenticación y autorización

    • Autenticación: identifica quién intenta acceder al clúster.
    • Autorización: decide si ese usuario o entidad tiene permiso para realizar la acción.
    • En Kubernetes, la combinación más habitual es:
      • usuarios o identidades federadas
      • certificados y tokens
      • RBAC (Role-Based Access Control) para dar permisos por roles
    RBAC
    • RBAC permite definir roles con permisos concretos y asignarlos a usuarios, grupos o service accounts.
    • Esto evita dar acceso administrativo completo a todo el clúster.
    • Ejemplo: un servicio puede leer ConfigMaps pero no gestionar deployments.

    Secrets y credenciales

    • Los secretos deben tratarse como información sensible y nunca como texto libre en el código.
    • Se usan para contraseñas, tokens, certificados y credenciales de acceso.
    • Se deben almacenar en sistemas seguros y limitar el acceso a ellos.
    • En AWS, se puede integrar con AWS Secrets Manager o SSM Parameter Store.

    ConfigMaps vs Secrets

    • ConfigMap: guarda configuración no sensible.
    • Secret: guarda datos sensibles.
    • Separar ambos reduce riesgos y facilita la gestión del entorno.

    Network policies

    • Las Network Policies permiten controlar el tráfico entre pods y entre namespaces.
    • Se pueden definir reglas de entrada y salida para limitar la comunicación.
    • Son importantes para aislar microservicios y reducir la superficie de ataque.

    Pod Security

    • Los contenedores no deben ejecutarse como root si no es necesario.
    • Se recomienda usar usuarios no privilegiados.
    • Reducir capacidades del contenedor (capabilities) y evitar permisos innecesarios.
    • Montar archivos de solo lectura cuando sea posible.
    • Usar imágenes confiables y mantenerlas actualizadas.

    Imágenes y vulnerabilidades

    • Las imágenes deben construirse desde bases confiables y verificadas.
    • Deben escanearse para detectar vulnerabilidades antes de desplegar.
    • En AWS, este control se complementa con servicios como Amazon ECR y Amazon Inspector.

    Seguridad en Amazon EKS

    • EKS gestiona el control plane, pero el usuario sigue siendo responsable de proteger los nodos, redes, IAM y workloads.
    • La seguridad en EKS se debe centrar en cuatro áreas principales:
      • identidad y permisos
      • red
      • nodos y workloads
      • secretos e imágenes

    IAM y EKS

    • Los nodos y pods deben usar permisos mínimos.
    • Los pods pueden asumir roles mediante IAM Roles for Service Accounts (IRSA).
    • Así un pod puede acceder a AWS services sin usar credenciales fijas en el código.
    • Esto reduce la exposición de secretos y mejora la trazabilidad.

    Red y VPC

    • Los clústeres EKS suelen ejecutarse dentro de una VPC.
    • Se recomienda usar subredes privadas para nodos y workloads sensibles.
    • Controlar el acceso con Security Groups y Network ACLs.
    • Limitar el acceso al API server y usar endpoints privados cuando sea posible.

    Grupos de nodos y seguridad

    • Los node groups deben cumplir el principio de mínimo privilegio.
    • Los nodos deben estar en subredes adecuadas y con políticas de seguridad restrictivas.
    • Se deben aplicar actualizaciones y parches regulares.

    Encriptación

    • Los datos del clúster y los secretos deben estar cifrados cuando sea posible.
    • EKS puede usar AWS KMS para proteger claves y encriptar datos del clúster.
    • Los secretos en tránsito y en reposo deben protegerse con cifrado.

    Escaneo de vulnerabilidades

    • Amazon Inspector puede ayudar a detectar vulnerabilidades en imágenes y aplicaciones.
    • ECR también ofrece control de versiones, artefactos y trazabilidad.
    • Esto permite detectar riesgos antes de que el software llegue a producción.

    Buenas prácticas de seguridad en EKS

    • Usar IAM Roles for Service Accounts en lugar de credenciales hardcodeadas.
    • Limitar permisos con RBAC y políticas IAM mínimas.
    • No ejecutar contenedores como root.
    • Usar Network Policies y segmentación por namespaces.
    • Proteger secretos y no versionarlos en repositorios.
    • Mantener imágenes actualizadas y escaneadas.
    • Revisar logs, métricas y alertas de seguridad.
    • Asegurar actualizaciones del control plane y nodos.

    Resumen

    • Kubernetes aporta mecanismos de seguridad, pero requieren configuración correcta.
    • EKS gestiona parte del control plane, pero la seguridad de la aplicación sigue siendo responsabilidad del usuario.
    • La clave está en combinar IAM, RBAC, secretos seguros, redes restringidas, imágenes verificadas y monitorización continua.

    Amazon GuardDuty

    • Amazon GuardDuty es un servicio de detección de amenazas y análisis de seguridad para AWS.
    • Monitoriza continuamente actividades sospechosas en la cuenta y en los servicios del entorno, incluyendo EKS.
    • Puede analizar logs de auditoría, VPC Flow Logs, DNS, CloudTrail y eventos del control plane de Kubernetes.
    • Para EKS, puede detectar comportamientos anómalos relacionados con el acceso al clúster, comunicaciones sospechosas o actividad maliciosa.
    • No se basa solo en reglas estáticas: también usa análisis de comportamiento, correlación de señales y patrones de actividad para detectar amenazas que no encajan con el uso normal del entorno.
    • En el control plane de EKS, esto es especialmente útil porque el control plane registra operaciones críticas del clúster: crear deployments, modificar RBAC, exponer servicios, cambiar roles, acceder a secretos, etc.
    • Si una identidad o un pod intenta hacer actividad rara o desproporcionada, GuardDuty puede generar un hallazgo de seguridad.
    • Emite hallazgos que pueden enviarse a EventBridge, CloudWatch o integrarse con otros servicios de seguridad.
    • Relación con el control plane: el control plane es el punto central de gestión del clúster, y GuardDuty vigila ese flujo de operaciones para detectar comportamientos sospechosos y posibles ataques o compromisos.

    AWS Detective

    • AWS Detective ayuda a investigar incidentes de seguridad y entender qué ha ocurrido en la cuenta.
    • Recopila y analiza datos de diferentes fuentes de seguridad, como GuardDuty, VPC Flow Logs, CloudTrail y otros eventos de AWS.
    • Permite seguir la pista de una actividad sospechosa, ver cómo se propagó y comprender el alcance del problema.
    • Es muy útil en incident response, porque ayuda a reconstruir la historia del ataque o del comportamiento anómalo.
    • En un entorno EKS, permite correlacionar eventos del clúster con otros servicios de AWS para identificar la causa raíz.

    AWS Security Hub

    • AWS Security Hub es un servicio de gestión de seguridad centralizada y cumplimiento.
    • Agrega y consolida hallazgos de seguridad procedentes de GuardDuty, Inspector, IAM Access Analyzer, Firewall Manager y otros servicios.
    • Proporciona una vista centralizada para revisar riesgos, prioridades y cumplimiento en la cuenta.
    • Ayuda a estandarizar la seguridad en múltiples servicios y cuentas de AWS.
    • En EKS, puede integrar hallazgos sobre vulnerabilidades de imágenes, riesgos de configuración y detección de amenazas.

    Relación entre ellos

    • GuardDuty detecta amenazas y genera hallazgos.
    • Security Hub centraliza y organiza esos hallazgos para una visión global.
    • Detective ayuda a investigar y reconstruir el incidente a partir de los datos generados.
    • Juntos forman una capa útil de seguridad operativa para entornos Kubernetes y AWS.
