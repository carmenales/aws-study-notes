    Comparativa de Tipos de Almacenamiento: S3 vs. EBS vs. EFS

    AWS clasifica sus soluciones de almacenamiento primario en tres arquitecturas según la estructura de datos, el método de acceso y el nivel de concurrencia:

    Tabla Comparativa de Paradigmas de Almacenamiento

    Característica Amazon S3 Amazon EBS Amazon EFS
    Tipo de Almacenamiento Objetos (Object Storage) Bloques (Block Storage) Archivos en Red (File Storage / NAS)
    Protocolo de Acceso HTTP / HTTPS (API REST) Dispositivo de bloque virtual NFSv4.0 / NFSv4.1
    Volumen de Arranque (Boot OS) No Sí (Volumen raíz del SO para EC2) No (Almacenamiento de datos compartidos)
    Alcance y Resiliencia Global a nivel de Región (mínimo 3 AZs) Delimitado a una única Zona de Disponibilidad (AZ) Regional (Multi-AZ simultáneo)
    Concurrencia de Acceso Ilimitada vía web / APIs Una sola instancia (salvo Multi-Attach io1/io2 en la misma AZ) Miles de instancias EC2 concurrentes en múltiples AZs
    Alojamiento Web Estático Sí (Nativo para HTML/CSS/JS) No (Requiere servidor web en ejecución) No (Requiere servidor web en ejecución)
    Escalabilidad de Capacidad Elástica e ilimitada de forma automática Tamaño aprovisionado fijo por volumen (ampliable dinámicamente) Elástica automática según el volumen de archivos

    Criterios Técnicos de Selección

    • Elegir Amazon S3:
      • Almacenamiento masivo de contenido no estructurado (archivos multimedia, documentos PDF, registros de logs, conjuntos de datos analíticos).
      • Alojamiento de interfaces web estáticas desacopladas de servidores de backend.
      • Almacén de copias de seguridad duraderas e inmutables (incluyendo snapshots de volúmenes EBS).
    • Elegir Amazon EBS:
      • Almacenamiento dedicado de alto rendimiento para el disco del sistema operativo de instancias EC2.
      • Motores de bases de datos relacionales o transaccionales que demandan latencias de acceso a disco submilisegundo y control de IOPS aprovisionados.
    • Elegir Amazon EFS:
      • Cargas de trabajo distribuidas donde múltiples servidores de aplicación o microservicios requieren acceso de lectura/escritura concurrente al mismo árbol de directorios.
      • Sistemas de gestión de contenidos (CMS como WordPress o Drupal), repositorios de código compartidos y procesamiento paralelo de archivos a través de múltiples AZs.

    Local Secondary Index (LSI) vs Global Secondary Index (GSI)

    • Local Secondary Index (LSI):

      • Tiene la misma clave de partición que la tabla base.
      • Puede tener una clave de ordenación diferente.
      • Está limitado a la misma partición de la tabla base.
      • Se usa cuando quieres consultar eficientemente un subconjunto de datos dentro de la misma partición.

    • Global Secondary Index (GSI):

      • Tiene una clave de partición distinta a la tabla base.
      • Puede tener su propia clave de ordenación.
      • Se puede consultar de forma independiente de la tabla base.
      • Se usa cuando quieres consultar datos con una clave distinta y escalar la consulta a través de particiones diferentes.

    En resumen:

    • LSI: misma clave de partición que la tabla base, distinta clave de ordenación.
    • GSI: distinta clave de partición y, normalmente, distinta forma de acceso.

    Prefijos y Rendimiento de Peticiones en Amazon S3 (Throughput & Partitioning)

    Amazon S3 es un almacenamiento plano de objetos (clave-valor) donde no existen carpetas reales, sino nombres de clave que incluyen prefijos lógicos delimitados comúnmente por /.

    Particionado Físico y Escalado de Throughput

    S3 escala automáticamente el rendimiento particionando el almacenamiento interno por prefijos. Cada prefijo independiente cuenta con una tasa base de peticiones por segundo:

    • 5.500 peticiones/s para lecturas (GET, HEAD).
    • 3.500 peticiones/s para escrituras/mutaciones (PUT, COPY, POST, DELETE).

    Escalado Horizontal y Throughput Agregado

    No existe límite en el número de prefijos que se pueden crear en un bucket. Al distribuir los objetos entre prefijos paralelos, el rendimiento se multiplica linealmente:

    Número de Prefijos Paralelos Rendimiento de Lectura (GET/HEAD) Rendimiento de Escritura (PUT/POST/DELETE)
    1 prefijo 5.500 peticiones / seg 3.500 peticiones / seg
    10 prefijos 55.000 peticiones / seg 35.000 peticiones / seg
    100 prefijos 550.000 peticiones / seg 350.000 peticiones / seg

    Trampas y Patrones de Examen (DVA-C02 & DOP-C02)

    • Error HTTP 503 Slow Down: Se produce cuando una aplicación incrementa la tasa de peticiones sobre un mismo prefijo más rápido de lo que S3 tarda en dividir la partición interna.
      • Solución en código: Implementar reintentos con Exponential Backoff.
      • Solución arquitectónica: Distribuir las escrituras/lecturas entre múltiples prefijos paralelos.
    • Prefijos con hashes aleatorios (Patrón Legacy): Históricamente se añadían cadenas hexadecimales aleatorias al inicio del nombre de la clave (ejemplo: 23a6-archivo.jpg o f4c1-documento.pdf).

      Actualmente ya no es necesario, S3 gestiona el particionado automático sin necesidad de ofuscar o randomizar los nombres de clave.

    • Cuello de botella con SSE-KMS: Si los objetos se cifran con claves KMS (SSE-KMS), cada llamada a GET/PUT genera solicitudes kms:Decrypt o kms:GenerateDataKey. El límite de throughput suele verse frenado por las cuotas de peticiones de KMS en la región antes de alcanzar los límites de S3.
    • Lecturas masivas repetitivas: Si la demanda supera los límites de S3 y los objetos son estáticos, la respuesta de diseño correcta es colocar Amazon CloudFront como capa de caché CDN delante del bucket.

    CORS

    • CORS significa Cross-Origin Resource Sharing.
    • Permite que un navegador permita solicitudes HTTP desde un origen distinto al del recurso que las está sirviendo.
    • Es necesario cuando una web frontend, por ejemplo en https://app.example.com, hace peticiones a una API en otro dominio, como https://api.example.com.
    • Sin CORS, el navegador bloquearía esa solicitud por seguridad.
    • En el contexto de JavaScript, esto aparece normalmente cuando un frontend ejecutado en el navegador hace fetch o axios a una API distinta.
    • La política la aplica el navegador, no el propio JavaScript, y por eso CORS suele aparecer como un problema de frontend y de seguridad.

    Rol en API Gateway:

    • API Gateway puede configurar CORS para permitir que un frontend externo consuma la API.
    • Se suele habilitar en el recurso o API completa mediante un configurador de CORS.
    • Permite definir métodos HTTP permitidos, headers y orígenes autorizados.

    Finalidad y propósito:

    • Permitir el acceso controlado entre distintos orígenes.
    • Mantener la seguridad del navegador mientras se habilita el intercambio legítimo de datos.
    • Evitar que cualquier sitio web pueda llamar a tu API sin control.

    Datos relevantes para certificación:

    • CORS es una política del navegador, no del servidor en sí mismo.
    • El servidor debe responder con los headers adecuados, como Access-Control-Allow-Origin.
    • API Gateway puede gestionar CORS para que la API sea consumida por un frontend externo.
    • Se suelen configurar Allow-Origin, Allow-Methods, Allow-Headers y Expose-Headers.
    • Es importante para aplicaciones frontend que consumen APIs REST desde un dominio diferente.

    Quota y Throttling

    Quota

    • Es el límite máximo permitido por un servicio, cuenta o recurso.
    • Puede ser un número de API calls por segundo, número de instancias, tamaño de almacenamiento o número de objetos por bucket.
    • AWS ofrece quotas por defecto y algunos pueden solicitarse para aumentarlos mediante Service Quotas.
    • En certificación, conviene recordar que quota es un límite configurado o permitido, no un fallo de ejecución.

    Throttling

    • Acelerar y desacelerar.
    • Es el proceso por el cual AWS limita o rechaza peticiones cuando se excede la capacidad o la tasa permitida.
    • Suele aparecer como 429 Too Many Requests, ThrottlingException o errores similares.
    • Es un problema de tasa de uso o de capacidad, no de autenticación.
    • En diseño, se resuelve con reintentos, backoff exponencial, cola de mensajes o escalado de capacidad.

    Diferencia clave

    • Quota: límite máximo autorizado.
    • Throttling: respuesta cuando ese límite se excede o la capacidad disponible es insuficiente.

    Relevancia para DVAC02:

    • En APIs y servicios distribuidos, es importante entender que una aplicación puede fallar por exceso de consumo o por límites del servicio.
    • Hay que diseñar para manejar errores de throttling y conocer que los quotas pueden requerir solicitud de aumento.

    Security Token Service (STS)

    • assume-role: asumir credenciales temporales
    • decode-authorization-message: Decodifica información adicional sobre el estado de autorización de una solicitud de un mensaje codificado devuelto en una respuesta de una solicitud de AWS.
    • get-access-key-info: Devuelve el id de la cuenta para un ID de una clave de acceso específicada
    • get-caller-identity: Devuelve detalles sobre el usuario o rol IAM cuyo credenciales son usadas para la operación de llamada.
    • get-delegated-access-token: Convierte un token de intercambio en credenciales temporales de AWS para un principal específico, permitiendo delegar acceso a recursos con permisos asociados al rol o identidad asumida.
    • get-federation-token: Devuelve credenciales temporales de seguridad para un usuario, normalmente para aplicaciones proxy que necesitan acceder a AWS en nombre de aplicaciones distribuidas dentro de una red corporativa.

    Diferencia entre get-delegated-access-token y get-federation-token

    • get-delegated-access-token se usa para obtener credenciales temporales a partir de un token de intercambio y delegar acceso a un principal concreto.
    • get-federation-token se usa para generar credenciales temporales para un usuario IAM, normalmente en aplicaciones proxy o entornos distribuidos.

    Accesos Multi-Cuenta (Cross-Account Access)

    • Para auditar o permitir que una aplicación ejecutada en la Cuenta A acceda a servicios de AWS en la Cuenta B o C, se debe configurar una arquitectura basada en roles de acceso cruzado.
    • Se debe crear un rol IAM en cada cuenta auditada (Cuentas B y C) configurando la Cuenta A como entidad de confianza. La aplicación en la Cuenta A debe utilizar la API AssumeRole del SDK de AWS para obtener credenciales temporales y ejecutar llamadas sobre los recursos remotos.

    Identity and Access Management (IAM)

    Tipos de Políticas en AWS

    Las políticas de IAM son documentos JSON estructurados que determinan la autorización sobre las llamadas a las APIs de los servicios de AWS. Se dividen funcionalmente en dos grandes categorías:

    1. Políticas de Concesión de Permisos (Grant Permissions)

    Son las únicas políticas que otorgan permisos de acceso efectivos directos:

    • Identity-Based Policies (Políticas basadas en identidad): Se adjuntan directamente a usuarios, grupos de IAM o roles de IAM. Definen qué acciones (Action) puede realizar ese principal sobre qué recursos (Resource) y bajo qué condiciones (Condition). Pueden ser Managed Policies (gestionadas por AWS o por el cliente) o Inline Policies (embebidas directamente en la identidad).
    • Resource-Based Policies (Políticas basadas en recursos): Se adjuntan directamente al recurso de destino (por ejemplo, Amazon S3 Bucket Policies, Amazon SQS Queue Policies, AWS KMS Key Policies). Especifican qué principales tienen permiso para interactuar con dicho recurso y admiten accesos directos cross-account sin requerir asunción de rol.

    2. Políticas Delimitadoras de Permisos Máximos (Set Maximum Permissions / Guardrails)

    No conceden permisos por sí mismas; establecen el límite máximo de permisos que una política basada en identidad puede llegar a otorgar:

    • IAM Permissions Boundaries: Mecanismo avanzado que fija el límite máximo de privilegios (maximum permissions) que una política basada en identidad puede llegar a otorgar a un usuario o rol.
    • AWS Organizations Service Control Policies (SCPs): Establecen la barrera máxima de permisos a nivel jerárquico dentro del árbol de AWS Organizations (Unidades Organizativas - OUs o Cuentas miembro). Si una SCP no permite o deniega explícitamente una acción, ninguna identidad de la cuenta afectada podrá ejecutarla.
    • Session Policies: Políticas en formato JSON que se pasan como parámetro durante la asunción programática de un rol o credenciales temporales vía AWS STS (llamadas a AssumeRole, AssumeRoleWithWebIdentity o GetFederationToken). Limitan la sesión activa a la intersección exacta entre las políticas del rol y la Session Policy.

    Reglas de Decisión del Algoritmo

    • Denegación por Defecto (Default Deny): Toda solicitud a la API inicia en estado de denegación implícita. Si ninguna sentencia autoriza explícitamente la acción, se rechaza la petición.
    • Precedencia de Denegación Explícita (Explicit Deny): Una sentencia con "Effect": "Deny" en cualquier política aplicable anula cualquier "Effect": "Allow", independientemente del nivel en el que se encuentre.
    • Requisito de Permiso Explícito (Explicit Allow): Para que una petición sea aprobada en ausencia de denegaciones explícitas, debe encontrarse al menos una declaración "Effect": "Allow" aplicable en la cadena de políticas.
    • Evaluación de Límites Máximos: Si existen SCPs, Permissions Boundaries o Session Policies, la acción solicitada debe figurar explícitamente permitida en cada uno de estos filtros; de lo contrario, se produce una denegación implícita por límite de barrera.

    Permissions Boundaries y Administración Delegada

    • Permisos Efectivos (Effective Permissions): Los permisos con los que opera efectivamente una identidad corresponden a la intersección matemática entre los permisos otorgados por sus políticas basadas en identidad (Identity-Based Policies) y el límite fijado por su Permissions Boundary.

    Patrón de Administración Delegada (Delegated Administration)

    Permite delegar en administradores secundarios (ej. jefes de equipo de desarrollo) la creación de usuarios y roles sin concederles la capacidad de elevar sus propios privilegios a nivel de cuenta (Privilege Escalation):

    • La política del administrador delegado le autoriza a ejecutar acciones como iam:CreateUser, iam:PutUserPolicy y iam:AttachUserPolicy condicionadas mediante la clave iam:PermissionsBoundary.
    • Obliga a que cualquier nuevo usuario o rol lleve adjunto de forma obligatoria un Permissions Boundary predefinido. Si el administrador delegado intenta crear un usuario sin asociar dicho boundary, la llamada a la API es rechazada.

    Modelado de Identidades y Gestión de Credenciales

    Usuarios, Grupos y Roles

    • Usuarios de IAM: Identidades estáticas con credenciales permanentes de largo plazo (contraseñas para la consola o Access Keys para CLI/SDK) asociadas a una persona o sistema.
    • Grupos de IAM: Contenedores lógicos de usuarios para asignar permisos comunes. Los grupos no pueden contener otros grupos (no admiten anidación), no pueden ser referenciados como Principal en Resource-Based Policies y no son identidades asumibles.
    • Roles de IAM: Identidades configurables asumibles de forma temporal por personas, aplicaciones o servicios de AWS (como Amazon EC2 o AWS Lambda). Al asumir un rol mediante la API sts:AssumeRole, AWS STS genera credenciales efímeras con caducidad automática compuestas por AccessKeyId, SecretAccessKey y SessionToken.

    Asunción de Roles a Nivel de Grupo

    Si una política adjunta a un grupo de IAM concede permisos para ejecutar sts:AssumeRole sobre un rol específico, todos los usuarios pertenecientes a dicho grupo adquieren la capacidad de asumir ese rol para elevar privilegios temporalmente o interactuar con recursos específicos.

    Resource-Based Policies vs. Identity-Based Policies

    Las políticas de IAM se diferencian estructuralmente y por su ámbito de aplicación según dónde se alojen:

    • Resource-based policy:

      • Se adjunta directamente al recurso (ej. S3 Bucket Policy, SQS Queue Policy, KMS Key Policy).
      • Sirve para decir: "este recurso permite acceso a este principal".
      • Característica clave: Incluye obligatoriamente el elemento Principal dentro de su estructura JSON para especificar explícitamente quién tiene acceso.
      • Se usa cuando quieres dar acceso desde otra cuenta (cross-account), desde un usuario concreto o incluso de forma pública.
      • Ejemplo típico: Una política de bucket S3 que permite a otra cuenta leer objetos.

    • Identity-based policy:

      • Se adjunta a una identidad: usuario, grupo o rol de IAM.
      • Sirve para decir: "esta identidad tiene estos permisos sobre estos recursos".
      • Característica clave: No incluye el elemento Principal en su JSON, ya que el sujeto está implícitamente definido por la identidad a la que se asocia la política.
      • Se usa cuando quieres que un usuario o rol pueda realizar operaciones en varios recursos.
      • Ejemplo típico: Un rol que puede listar y descargar objetos de S3.

    En resumen:

    • Resource-based policy: “Protege el recurso” especificando quién puede acceder a él mediante el campo Principal.
    • Identity-based policy: “Define lo que puede hacer la identidad” sobre un conjunto de recursos.

    Patrones Avanzados en Resource-Based Policies (Excepciones por Denegación)

    Uso de políticas de recursos con Effect: Deny combinadas con condiciones de exclusión (StringNotLike o StringNotEquals) para proteger recursos críticos:

    • Ejemplo de Estructura de Bloqueo por Excepción: 
      {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RestrictBucketAccess",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::MyExampleBucket",
        "arn:aws:s3:::MyExampleBucket/*"
      ],

        "StringNotLike": {
          "aws:userId": [
            "AROAEXAMPLEID:*",
            "111111111111"
          ]

Al tratarse de un Deny explícito, prevalecerá de forma absoluta sobre cualquier política de identidad que intente conceder acceso.

    Relación con RBAC y ABAC

    • Las policies son reglas concretas de permiso.
    • RBAC organiza permisos por roles.
    • ABAC organiza permisos por atributos como departamento, entorno o tags.

    JSON de una policy

    • La estructura básica es muy parecida en ambos tipos de policy: se usa Version y Statement.
    • Statement es el bloque principal y contiene normalmente Effect, Action y Resource.
    • Effect indica si la regla permite o deniega el acceso: Allow o Deny.
    • Action define qué acción se permite o se deniega.
    • Resource define sobre qué recurso aplica la regla.
    • En una resource-based policy suele aparecer Principal, porque el recurso necesita indicar quién puede acceder.
    • En una identity-based policy normalmente no aparece Principal, porque la política ya está asociada a una identidad.
    • El JSON debe ser válido y cumplir con la sintaxis de IAM Policy.
    • En la práctica, los campos más importantes para recordar son: Effect, Action, Resource y, en algunas políticas, Principal.

    Seguridad y Cifrado (KMS, S3 y STS)

    Estrategias de Cifrado en Reposo en Amazon S3

    • SSE-S3 (Server-Side Encryption con S3-Managed Keys): AWS gestiona automáticamente las claves y el cifrado. Opción por defecto cuando se requiere cifrado en reposo sin gestión adicional ni costes extra de API.
    • SSE-KMS (Server-Side Encryption con AWS KMS Keys): AWS realiza el cifrado usando claves gestionadas en KMS. Obligatorio si se requiere un rastro de auditoría (audit trail) en AWS CloudTrail para registrar qué usuario/rol utilizó la clave y cuándo.
    • SSE-C (Server-Side Encryption con Customer-Provided Keys): El cliente almacena y envía su propia clave en los headers HTTP de cada petición. AWS realiza el algoritmo de cifrado en memoria pero nunca almacena la clave.
    • Client-Side Encryption: La aplicación cifra los datos localmente en su entorno antes de enviarlos a S3. Requerido cuando las políticas prohíben enviar datos en texto plano a la nube o las claves deben permanecer exclusivamente on-premises.

    Patrón Envelope Encryption y APIs de AWS KMS

    • Límite de KMS Encrypt (4 KB): La API kms:Encrypt solo puede cifrar cargas de hasta 4 KB. Para cifrar objetos más grandes (ej. archivos de 3 MB o 100 GB), es obligatorio usar Envelope Encryption (Cifrado de Sobre).
    • GenerateDataKey: Devuelve una clave de datos en texto plano (plaintext) y una copia cifrada de esa clave. La aplicación usa la clave en texto plano para cifrar los datos localmente, destruye la clave plana de la memoria y almacena la clave cifrada junto a los datos.
    • GenerateDataKeyWithoutPlaintext: Devuelve exclusivamente la copia cifrada de la clave. Útil para generar y almacenar claves para uso futuro sin exponerlas en memoria.

    Control de Accesos y Políticas en S3

    • Forzar Cifrado en Tránsito (HTTPS): Configura una Bucket Policy que deniegue ("Effect": "Deny") el acceso si la condición "aws:SecureTransport" es "false".
    • Forzar Cifrado en Reposo: Configura una Bucket Policy que deniegue la subida (s3:PutObject) si la petición NO contiene el header x-amz-server-side-encryption.
    • Protección contra Hotlinking: Elimina el acceso público de lectura del bucket y obliga a la aplicación a generar URLs Pre-firmadas (Pre-signed URLs) con un tiempo de expiración corto para servir imágenes/archivos solo a usuarios autenticados.
    • Bucle Infinito de Logs (Anti-patrón): Al habilitar Server Access Logging, el bucket de destino de los registros debe ser un bucket diferente. Guardar los logs en el mismo bucket provoca escrituras recursivas infinitas y costes masivos.

    Troubleshooting y Errores Frecuentes

    • Error Access Denied en PutObject con SSE-KMS: Ocurre cuando el usuario/rol IAM tiene permisos en S3 (s3:PutObject), pero su política carece del permiso explícito kms:GenerateDataKey sobre la clave de KMS.
    • ThrottlingException en SSE-KMS: Subir miles de objetos/seg a S3 con SSE-KMS puede agotar la cuota de peticiones de KMS. Solución: Solicitar un aumento de cuota de API a AWS Support e implementar Exponential Backoff con reintentos en el código.
    • Rotación Automática de Claves: Para cumplir con normativas de rotación anual sin esfuerzo operativo, habilita la rotación automática de claves en la configuración de la KMS Customer Managed Key (CMK).
    • Decodificar Errores de Autorización (AWS STS): Si la AWS CLI devuelve un mensaje de error de autorización codificado (Encoded authorization failure message), usa el comando aws sts decode-authorization-message para traducirlo a JSON legible.
    • Instance Metadata (EC2): Para obtener programáticamente la IP pública, IP privada o el ID de la instancia EC2 desde la propia máquina, realiza una petición HTTP GET a http://169.254.169.254/latest/metadata/.

    AWS Cognito

    Qué es

    • AWS Cognito es un servicio de autenticación y autorización para aplicaciones web y móviles.
    • Permite gestionar usuarios, registro, login, recuperación de contraseña y MFA sin construir la identidad desde cero.
    • Se usa con Amplify, API Gateway, AppSync, Lambda y frontend web/móvil.

    Para qué se usa

    • Añadir autenticación a una aplicación.
    • Soportar usuarios propios y proveedores federados (Google, Facebook, Amazon, Apple, SAML).
    • Emitir tokens JWT para autorizar peticiones a APIs.
    • Entregar credenciales temporales de AWS a usuarios autenticados mediante Identity Pools.

    Amazon Cognito Sync

    • Es un servicio de AWS y una biblioteca de cliente que permite sincronizar los datos de perfil y las preferencias de los usuarios (como el estado de un videojuego o configuraciones) en múltiples dispositivos sin necesidad de crear ni administrar un código backend propio.
    • Características principales:
      • Acceso sin conexión: Guarda los datos de forma local en el dispositivo para que la aplicación pueda leerlos o escribirlos sin internet.
      • Sincronización automática: Actualiza y armoniza la información en la nube y en los otros dispositivos del usuario en cuanto recupera la conexión.
      • Gestión de conflictos: Resuelve de manera automática los cambios simultáneos realizados en diferentes aparatos.
    • Recomendación de uso actual:
      • AWS AppSync: Es la alternativa moderna recomendada por Amazon para la sincronización de datos en tiempo real y colaboración entre múltiples usuarios.

    Aunque hoy en día AWS AppSync es más moderno, en el examen Cognito Sync sigue siendo la respuesta correcta para el escenario de "sincronizar datos de perfil de usuario y preferencias del juego a través de múltiples dispositivos móviles" de forma silenciosa mediante eventos push.

    Amazon Cognito User Pools

    • Un User Pool es un directorio de usuarios gestionado por Cognito.
    • Permite que los usuarios se registren, inicien sesión y usen MFA, atributos personalizados y recuperación de cuenta.
    • También puede integrarse con OAuth 2.0, OpenID Connect y Hosted UI.
    • En resumen: User Pool = autenticación de usuarios de la aplicación.

    Amazon Cognito Identity Pools (Federated Identities) y Control Granular de Acceso

    Los Identity Pools permiten intercambiar la autenticación de usuarios (procedente de Cognito User Pools o proveedores federados como Google, Facebook o SAML) por credenciales temporales de AWS (vía AWS STS), permitiendo a las aplicaciones cliente interactuar directamente con servicios de AWS (como Amazon S3 o DynamoDB) sin necesidad de pasar por una API intermedia.

    1. Patrón de Política Única para Múltiples Usuarios (Fine-Grained Access Control)

    Para restringir el acceso a nivel de usuario en un bucket compartido de S3 sin crear políticas individuales por cada persona, se utiliza la variable de contexto de Cognito ${cognito-identity.amazonaws.com:sub} en el elemento Resource:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::mi-bucket/private/${cognito-identity.amazonaws.com:sub}/*"
    }
  ]
}

    La variable ${cognito-identity.amazonaws.com:sub} resuelve dinámicamente el identificador único del usuario federado (Identity ID, ej. eu-west-1:1111-aaaa), garantizando que cada usuario únicamente pueda leer o escribir dentro de su propio prefijo privado en S3.

    Patrón Arquitectónico: Autenticación Reforzada (Step-Up Authentication)

    El patrón Step-Up Authentication eleva dinámicamente los requisitos de seguridad cuando un usuario autenticado intenta ejecutar una acción sensible (como una transferencia de fondos o modificación de datos críticos de la cuenta):

    • Flujo Operativo
      1. El cliente inicia sesión básica mediante Cognito User Pools y obtiene tokens JWT estándar.
      2. Al llamar a una ruta de alto privilegio (ej. /transfer), el Lambda Authorizer consulta la configuración de la API y el almacén de sesiones en Amazon DynamoDB para determinar si la acción exige validación reforzada.
      3. Si la sesión no registra la verificación adicional completada, el autorizador bloquea la ejecución y fuerza al cliente a completar un desafío secundario (como ingresar un código OTP vía SMS o WebAuthn) antes de autorizar la transacción.

    Relación con IAM y STS

    • El Identity Pool no sustituye a IAM ni a STS.
    • Cognito Identity Pool identifica al usuario o app federada y decide si puede obtener acceso a AWS.
    • STS es el servicio que genera las credenciales temporales de acceso.
    • IAM es quien define qué permisos finales tiene esa identidad temporal sobre los recursos de AWS.
    • En la práctica: Cognito Identity Pool + STS entregan credenciales temporales; IAM decide lo que esa identidad puede hacer.

    Diferencia clave

    • User Pools gestionan la identidad de la aplicación y el flujo de login.
    • Identity Pools gestionan el acceso a AWS con credenciales temporales.
    • IAM define permisos sobre AWS; Cognito define identidad de usuarios en la app.

    Resumen rápido

    • User Pools = autenticación de usuarios.
    • Identity Pools = autorización para usar AWS con credenciales temporales.
    • IAM = permisos sobre recursos de AWS.

    Amazon DynamoDB

    Local Secondary Index (LSI) vs Global Secondary Index (GSI)

    • LSI:
      • Tiene la misma clave de partición que la tabla base.
      • Puede tener una clave de ordenación diferente.
      • Está limitado a la misma partición de la tabla base.
      • Se usa cuando quieres consultar eficientemente un subconjunto de datos dentro de la misma partición.
    • GSI:
      • Tiene una clave de partición distinta a la tabla base.
      • Puede tener su propia clave de ordenación.
      • Se puede consultar de forma independiente de la tabla base.
      • Se usa cuando quieres consultar datos con una clave distinta y escalar la consulta a través de particiones diferentes.
    • Resumen:
      • LSI: misma clave de partición que la tabla base, distinta clave de ordenación.
      • GSI: distinta clave de partición y, normalmente, distinta forma de acceso.

    Patrón de Diseño: Almacenamiento de Objetos Grandes (S3 + DynamoDB)

    • El límite estricto: Un ítem (registro) en DynamoDB tiene un límite máximo de tamaño de 400 KB.
    • El Patrón Recomendado: Para aplicaciones que necesitan guardar metadatos (ej. detalles de un empleado) junto con archivos binarios pesados (ej. fotos de alta resolución), se combinan ambos servicios.
    • Paso 1: Guardar el archivo pesado en Amazon S3.
    • Paso 2: Guardar los metadatos de texto en DynamoDB, incluyendo la clave del objeto (Object Key) de S3 como un atributo más del ítem.
    • Paso 3: La aplicación consulta DynamoDB (GetItem) para leer los datos y usa esa clave para recuperar la foto directamente de S3 (GetObject).

    Guardar perfiles en una base de datos relacional (RDS) y fotos en un sistema de archivos (EFS) rompe el principio serverless y de bajo mantenimiento

    EFS está pensado para acceso concurrente desde múltiples instancias EC2, no para recuperación de imágenes individuales vía API web. DynamoDB + S3 es la opción ligera y escalable.

    Optimización de Consultas y Troubleshooting

    • Throttling (ProvisionedThroughputExceededException): Si recibes este error a pesar de que las métricas de CloudWatch parecen normales, es probable que tengas una "Hot Partition" (mucho tráfico hacia una misma clave). A nivel de aplicación, la primera acción siempre es implementar Exponential Backoff (retraso exponencial en los reintentos) en el código.
    • Scan vs. Query: Query es mucho más eficiente. Si obligatoriamente debes usar la operación Scan en una tabla grande, hazlo durante horas valle y utiliza Parallel Scans (escaneos paralelos) limitando la tasa para no afectar el rendimiento en producción.
    • BatchGetItem vs. TransactWriteItems:
      • BatchGetItem / BatchWriteItem: Permite recuperar/escribir múltiples elementos de golpe para ahorrar llamadas a la API, pero no garantiza atomicidad.
      • TransactWriteItems: Realiza cambios coordinados de "todo o nada" (ACID). Imprescindible para sistemas financieros, inventarios o transferencias de saldo entre usuarios.

    Operaciones de Rendimiento y Troubleshooting

    • Consumo de Capacidad: Las lecturas fuertemente consistentes (Strongly Consistent Reads) consumen el doble de rendimiento que las lecturas eventualmente consistentes.
    • Optimización de Scans: Si debes hacer un Scan a una tabla grande, hazlo en horas valle y utiliza Parallel Scans limitando la tasa de lectura para minimizar el impacto en el rendimiento.
    • Eliminación Automática (Time To Live - TTL): Para borrar registros antiguos (ej. posts de más de 48 horas), añade un atributo de tipo Number con un timestamp unix y configura el TTL sobre ese atributo. Es la forma más barata y eficiente (no usa capacidad aprovisionada).
    • Transacciones vs Lotes:
      • BatchWriteItem / BatchGetItem: Recupera/escribe múltiples elementos en una sola llamada para ahorrar llamadas API, pero no garantiza atomicidad (puede que unos fallen y otros no).
      • TransactWriteItems: Realiza cambios coordinados de "todo o nada". Ideal para sistemas financieros o intercambios de saldo.
    • Throttling en la Tabla Principal (GSI Underprovisioned): Si tu tabla principal tiene suficientes WCU, pero sigues recibiendo errores de Throttling al escribir masivamente, es porque el Índice Secundario Global (GSI) tiene la capacidad de escritura sub-aprovisionada y está frenando a la tabla principal.
    • Evitar Sobrescrituras (Overwrites): En aplicaciones con alta concurrencia (como e-commerce actualizando precios), la única forma de evitar que la actualización de un usuario sobrescriba la de otro sin revisión es usar Escrituras Condicionales (Conditional Writes).
    • Seguridad Web Identity Federation: Si un juego móvil autentica a usuarios mediante Google/Facebook y guarda los datos en DynamoDB, para asegurar que el usuario "A" solo modifique los datos del usuario "A", debes añadir a la política de IAM la condición: "dynamodb:LeadingKeys": ["${www.amazon.com:user_id}"].
    • DynamoDB Streams a Lambda: Si habilitas los streams pero tu función Lambda no se dispara con los cambios, el motivo es que te falta configurar el Event Source Mapping para conectar el stream con la función.

    AWS X-Ray

    Qué es

    • AWS X-Ray es el servicio de trazado distribuido de AWS que permite ver cómo una petición viaja a través de múltiples servicios y componentes de una aplicación.
    • Se usa para diagnosticar latencias, errores, cuellos de botella y fallos en arquitecturas distribuidas.

    Para qué se usa

    • Visualizar el flujo completo de una solicitud.
    • Identificar servicios implicados en una transacción.
    • Detectar dónde se está tardando o dónde falla una petición.
    • Ver un mapa de dependencias entre servicios y componentes.
    • Correlacionar logs, trazas y métricas para depurar problemas de rendimiento.

    Información relevante para DVAC02

    • X-Ray está orientado a observabilidad y troubleshooting.
    • Se suele usar con servicios como API Gateway, Lambda, EC2, ELB, ECS, EKS, DynamoDB, SQS y SNS.
    • Su valor principal es mostrar latencia, errores y relación entre servicios en una sola vista.
    • En exámenes, suele aparecer como una herramienta de diagnóstico y monitorización de trazas distribuidas.

    Implementación de Trazas

    • En EC2: Para monitorizar una aplicación desplegada en instancias EC2 con AWS X-Ray, instala el demonio de X-Ray (X-Ray daemon) e instrumenta el código de la aplicación. Además, asegúrate de que el rol de la instancia (Instance Role) tenga los permisos xray:PutTraceSegments y xray:PutTelemetryRecords.
    • En ECS: Para habilitar X-Ray en una aplicación dentro de Amazon ECS, debes crear una imagen Docker que ejecute el demonio de X-Ray, añadir instrumentación al código de la aplicación para X-Ray, y configurar un rol de IAM para las tareas (Task Role).

    Conceptos Estructurales: Traces, Segments y Subsegments

    AWS X-Ray recopila datos sobre las solicitudes que atiende la aplicación y los estructura de forma jerárquica:

    • Trace (Traza): Representa la ruta completa de una solicitud de extremo a extremo a través de todos los servicios y componentes distribuidos[cite: 14].
    • Segment (Segmento): Registra el trabajo realizado por un servicio o recurso de computación individual (ej. el servicio AWS Lambda o una instancia EC2)[cite: 14].
    • Subsegment (Subsegmento): Desglosa el trabajo interno dentro de un segmento principal. Permite medir tiempos de bloques de código personalizados (ej. una operación de CPU intensiva) o llamadas a servicios descendentes (ej. llamadas a DynamoDB, S3 o APIs HTTP externas)[cite: 14].

    Amazon CloudWatch

    Qué es

    • Amazon CloudWatch es el servicio de observabilidad y monitorización de AWS.
    • Permite recopilar métricas, logs y eventos de los servicios de AWS y de las aplicaciones.
    • También se usa para activar alarmas y responder a cambios de estado en los recursos.

    Para qué se usa

    • Monitorizar el estado de recursos como EC2, Lambda, API Gateway, RDS, DynamoDB y más.
    • Crear alarmas para notificar cuando una métrica supera o baja de un umbral.
    • Recolectar logs con CloudWatch Logs.
    • Generar dashboards para visualizar el comportamiento de la infraestructura o la aplicación.
    • Automatizar respuestas con alarmas y eventos.

    Métricas Personalizadas (Custom Metrics)

    Para monitorizar gráficamente valores específicos generados por tu aplicación (como el número de hilos en ejecución a lo largo del tiempo), la forma más eficiente es crear una métrica personalizada en Amazon CloudWatch y realizar llamadas periódicas a la API PutMetricData.

    Amazon CloudWatch: Métricas Clave para ECS y Lambda

    Para la observabilidad y el diagnóstico de rendimiento operativo en arquitecturas serverless y de contenedores, se deben supervisar las siguientes métricas estándar:

    Métricas de AWS Lambda

    • Invocations: Número total de ejecuciones de la función (exitosas y fallidas).
    • Errors: Número de invocaciones que han finalizado con una excepción no controlada en el código.
    • Duration: Tiempo transcurrido desde que la función comienza a ejecutarse hasta que finaliza (permite detectar cuellos de botella y ajustar la memoria asignada).
    • Throttles: Número de invocaciones bloqueadas porque la concurrencia simultánea ha alcanzado el límite reservado o de la cuenta.
    • ConcurrentExecutions: Número de instancias de ejecución procesando eventos de manera simultánea en un momento dado.

    Métricas de Amazon ECS (Elastic Container Service)

    • CPUUtilization: Porcentaje de unidades de CPU reservadas o utilizadas por las tareas o el clúster en ejecución.
    • MemoryUtilization: Porcentaje de memoria asignada que está siendo consumida por los contenedores de las tareas activas.

    Información relevante para DVAC02

    • Se centra en rendimiento, disponibilidad, métricas y logs.
    • Es la herramienta principal para observabilidad en AWS.
    • Suele ser una solución para monitorización, alertas y diagnóstico operacional.
    • CloudWatch Logs permite guardar y consultar logs de servicios y aplicaciones.
    • CloudWatch Metrics se usa para métricas numéricas y tiempo real.

    AWS CloudTrail

    Qué es

    • AWS CloudTrail es el servicio de auditoría y trazabilidad de acciones realizadas en una cuenta de AWS.
    • Registra eventos de API y actividades de gestión, mostrando quién hizo qué, cuándo y desde qué origen.
    • Se usa para seguridad, cumplimiento, análisis forense y control de cambios.

    Para qué se usa

    • Ver quién ha hecho cambios en la cuenta.
    • Auditar acciones sobre servicios de AWS.
    • Investigar incidentes de seguridad o errores operativos.
    • Identificar acciones de usuarios, roles, servicios y aplicaciones sobre recursos.
    • Comprobar eventos de administración y uso de API.

    Información relevante para DVAC02

    • CloudTrail está orientado a trazabilidad y seguridad.
    • Se usa para responder preguntas como “quién hizo esto”, “qué acción se ejecutó” y “cuándo ocurrió”.
    • En certificación, es clave distinguirlo de CloudWatch: CloudTrail responde a la auditoría de acciones, mientras CloudWatch responde a la observabilidad del rendimiento y del estado.

    Diferencia clave entre CloudWatch y CloudTrail

    • CloudWatch:
      • Monitoriza y observa el estado de los servicios y aplicaciones.
      • “¿cómo está funcionando?”
    • CloudTrail:
      • registra y audita las acciones realizadas en la cuenta de AWS.
      • “¿qué se ha hecho?”

    Amazon EventBridge

    Enrutamiento de eventos entre cuentas (Cross-Account Event Routing)

    • EventBridge permite enviar y recibir eventos entre diferentes cuentas de AWS.
    • Es el patrón recomendado para centralizar eventos de múltiples cuentas en una sola cuenta principal (logging, auditoría, procesamiento centralizado).
    • Los servicios de AWS (como EC2) solo envían sus eventos de forma nativa al bus de eventos (event bus) de su propia cuenta.
    • Los servicios de AWS no pueden enviar eventos directamente al bus de otra cuenta sin pasar primero por su propio bus.

    Pasos para configurar el envío Multi-Cuenta

    • Paso 1 (Cuenta Receptora): Editar las políticas de recursos (resource-based policies) del bus de eventos principal para permitir que las cuentas emisoras puedan enviarle eventos.
    • Paso 2 (Cuentas Emisoras): Crear una regla de EventBridge que capture los eventos locales deseados (ej. cambios de estado de EC2).
    • Paso 3 (Cuentas Emisoras): Configurar como destino (target) de esa regla el bus de eventos de la cuenta receptora.
    • Paso 4 (Cuenta Receptora): Crear una regla adicional en el bus principal que capture los eventos entrantes y los enrute hacia el destino final (ej. una cola SQS, Lambda, etc.).

    Consideraciones clave para certificación

    • Las reglas de la cuenta emisora no deben apuntar directamente al recurso final (como SQS) en la otra cuenta.
    • El flujo oficial siempre requiere pasar por un event bus intermedio en la cuenta de destino.
    • Un enfoque de "polling" o escaneo (como usar una Lambda cada minuto para revisar estados de EC2) es ineficiente y es considerado una mala práctica (anti-pattern) frente a la arquitectura orientada a eventos nativa de EventBridge.

    Amazon Elastic Container Service (ECS)

    Gestión de Secretos y Configuración (FEWEST application changes)

    • La mejor práctica para inyectar configuración (URLs) y datos sensibles (credenciales) en contenedores ECS es usar AWS Systems Manager Parameter Store o AWS Secrets Manager.
    • Minimizar cambios en el código: ECS se integra de forma nativa con ambos servicios. En la definición de tarea (Task Definition), se usa el campo secrets referenciando el ARN del parámetro o secreto.
    • ECS recupera el valor automáticamente durante el arranque y lo inyecta como una variable de entorno estándar dentro del contenedor.
    • La aplicación no requiere importar el SDK de AWS ni cambiar su código; simplemente lee variables de entorno normales (ej. process.env.API_URL).

    Permisos y Variables de Entorno en ECS

    • Permisos mínimos (Least Privilege): Para otorgar privilegios mínimos a distintos microservicios en ECS (ej. uno que lee RDS Aurora y otro que lee DynamoDB), debes configurar cada definición de tarea (Task Definition) para que referencie un rol de IAM distinto con los accesos necesarios para ese servicio. En las instancias EC2 subyacentes, debes configurar ECS_ENABLE_TASK_IAM_ROLE a true en el archivo de configuración del agente de ECS.
    • Inyección de Variables de Entorno: Para pasar variables de entorno a un contenedor en Amazon ECS (incluyendo entornos Fargate), define un array bajo el parámetro environment dentro de la definición de la tarea (Task Definition).

    Security

    AWS KMS vs Parameter Store vs Secrets Manager

    • AWS KMS: Es el motor de cifrado subyacente. No es un almacén de clave-valor. Una aplicación nunca debe consultar directamente a KMS para obtener una variable de configuración o un texto. KMS trabaja por debajo cifrando lo que guardan Parameter Store y Secrets Manager.
    • Systems Manager Parameter Store: Ideal para guardar configuración general (URLs de APIs) y secretos básicos. Su gran ventaja es organizar variables en jerarquías de rutas por entorno (ej. /dev/api-url o /prod/api-url).
    • Secrets Manager: Ideal para credenciales de bases de datos. Sus ventajas exclusivas frente a Parameter Store son la rotación automática de credenciales (usando una Lambda por detrás), la generación de contraseñas aleatorias y la facilidad para compartir secretos entre cuentas (cross-account).

    S3

    S3 Object Lambda

    • Es una característica que permite ejecutar código propio (una función Lambda) para procesar y modificar los datos de un objeto de S3 en tiempo real durante una solicitud GET.
    • Mantiene una única copia del objeto original en el bucket (ahorrando costes de almacenamiento y cumpliendo normativas de inmutabilidad).
    • Funciona mediante un S3 Object Lambda Access Point. Si el usuario accede por este punto, recibe el archivo transformado. Si accede por el punto de acceso estándar de S3, recibe el archivo original.
    • Casos de uso clave para certificación: Ocultar/redactar datos sensibles (PII) según quién hace la petición, convertir formatos de datos sobre la marcha (ej. XML a JSON) o redimensionar imágenes instantáneamente al descargarlas.

    Detalles y Troubleshooting

    • Límite de tamaño (5 GB vs 5 TB): Aunque S3 admite archivos de hasta 5 TB, una única operación PUT tiene un límite estricto de 5 GB. Si intentas subir un archivo mayor (ej. 6 GB) de golpe, fallará con el error Your proposed upload exceeds the maximum allowed object size. La solución obligatoria es usar la Multipart Upload API.
    • Robo de ancho de banda (Hotlinking): Si sitios web externos están enlazando las imágenes de tu S3 y generando altos costes, debes quitar el acceso público de lectura y forzar a tu aplicación a generar URLs Pre-firmadas (Pre-signed URLs) con una caducidad corta (ej. 15 minutos).

    Anti-patrones para el examen (Lo que NO debes hacer en S3)

    • Usar S3 Event Notifications para interceptar un GET: Las notificaciones de eventos de S3 son asíncronas y se disparan ante cambios de estado (PUT, POST, DELETE). Es imposible usar un evento clásico de S3 para transformar un archivo mientras un usuario hace un GET. Para eso existe S3 Object Lambda.
    • Modificar el archivo en el evento PUT para ocultar PII: Si una Lambda modifica el archivo en el momento de la subida (PUT), sobrescribirá el archivo o creará una segunda copia modificada. Esto viola los requisitos legales de mantener el registro original inmutable.
    • GetObjectLegalHold: Esta API no sirve para transformar contenido ni ocultar datos. Está relacionada exclusivamente con S3 Object Lock para consultar si un objeto está bloqueado legalmente contra eliminación o sobrescritura (cumplimiento normativo WORM).

    AWS Lambda

    Ciclo de Vida del Runtime Environment y Almacenamiento Temporal (/tmp)

    AWS Lambda ejecuta el código dentro de un entorno de ejecución (Runtime Environment) aislado que incluye CPU, memoria asignada, red y un sistema de archivos efímero (/tmp).

    Invocación vs. Ciclo de Vida del Entorno

    • Duración máxima de una invocación: 15 minutos por llamada individual.
    • Ciclo de vida del Entorno: AWS inicializa el entorno en el primer evento (Cold Start) y lo mantiene en espera (Warm / Inactivity period) tras finalizar la ejecución.
    • Destrucción no programada: AWS no notifica cuándo destruye un entorno inactivo; es una decisión interna basada en la demanda de la infraestructura. Si el entorno se destruye, la siguiente petición sufrirá un nuevo Cold Start.
    • Modelo de Concurrencia (1 a 1): Un entorno de ejecución solo puede procesar una solicitud a la vez. Si llegan múltiples eventos simultáneos, AWS aprovisiona entornos paralelos independientes (Environment 1, Environment 2, etc.), cada uno con su propio arranque en frío.

    Comportamiento del Directorio /tmp (Almacenamiento Efímero)

    • /tmp no es un volumen persistente (no es EBS ni EFS):
      • Persistencia entre Warm Starts: Los archivos escritos en /tmp se conservan disponibles para invocaciones posteriores únicamente si son atendidas por el mismo entorno de ejecución activo.
      • Pérdida de datos: Cuando AWS destruye el entorno de ejecución, todo el contenido de /tmp se borra definitivamente.
    • Capacidad de almacenamiento: Tamaño base de 512 MB (configurable hasta 10.240 MB / 10 GB).
    • Ruta de acceso en código:
      • En entornos Linux (estándar de Lambda): /tmp
      • En pruebas locales Windows: C:\Users\<Usuario>\AppData\Local\Temp

    Patrones de Diseño y Claves de Certificación

    • Patrón de Caché en /tmp: Para acelerar ejecuciones warm, el código debe verificar si un recurso pesado (ej. un modelo de Machine Learning o un archivo de configuración descargado de S3) ya existe en /tmp. Si existe, se reutiliza; si no, se descarga.
    • Reutilización de Conexiones: La inicialización de clientes del SDK (DynamoDB, S3) y conexiones a bases de datos (RDS) debe ubicarse fuera del handler (ámbito global) para aprovechar que el entorno de ejecución se reutiliza entre invocaciones sucesivas.
    • Persistencia Real: Si la aplicación requiere que múltiples funciones Lambda concurrentes compartan archivos o que los datos sobrevivan a la destrucción del entorno, la solución arquitectónica obligatoria es montar Amazon EFS.

    Creación de Funciones Lambda mediante AWS CLI

    Para desplegar una función de forma programática utilizando la línea de comandos, se emplea la operación create-function:

    aws lambda create-function \
    --function-name ProcessDynamoDBRecords \
    --zip-file fileb://function.zip \
    --handler index.handler \
    --runtime nodejs12.x \
    --role arn:aws:iam::123456789012:role/lambda-dynamodb-role

    Parámetros

    • --zip-file fileb://...: El prefijo fileb:// es obligatorio en la AWS CLI cuando se cargan archivos binarios (como un paquete .zip), indicando que el contenido debe manejarse de forma binaria.
    • --handler: Especifica el punto de entrada de la ejecución con el formato archivo.funcion. Por ejemplo, index.handler busca la función exportada llamada handler dentro del archivo index.js.
    • --role (Lambda Execution Role):
      • Define el rol de ejecución que la función Lambda asumirá automáticamente en tiempo de ejecución para obtener credenciales temporales y acceder a otros servicios de AWS (por ejemplo, leer o escribir en una tabla de Amazon DynamoDB).

        Este rol no debe confundirse con las credenciales locales que utiliza el desarrollador o la máquina (PC) para ejecutar el comando de la AWS CLI.

    Estructura del Código y Objetos de Contexto (Node.js)

    Ejemplo de implementación de un manejador (handler) asíncrono en Node.js:

    // index.js
exports.handler = async (event, context) => {
    console.log("Evento recibido:");
    console.log(JSON.stringify(event, null, 2));

    return {
        statusCode: 200,
        body: JSON.stringify({
            message: "¡Hola Mundo desde Lambda!",
            function: context.functionName,
            requestId: context.awsRequestId
        })
    };
};

    Objeto event vs. Objeto context

    • event: Contiene los datos y la carga útil (payload) proporcionados por el servicio disparador (event source) que invoca la función.
    • context: Proporciona información sobre el entorno de ejecución en tiempo real. Entre sus atributos destacan:
      • context.awsRequestId: Identificador único de la invocación actual, fundamental para la correlación y depuración de logs en Amazon CloudWatch Logs.
      • context.functionName: Nombre de la función Lambda en ejecución.

    Almacenamiento Temporal, Rendimiento y Despliegues Seguros

    • Directorio /tmp: Si tu función AWS Lambda necesita crear archivos temporales (por ejemplo, menores a 10 MB) para ser accedidos y modificados durante la ejecución, guárdalos en el directorio /tmp.
    • Aumento de Capacidad Compute: Si descubres que incrementar la capacidad de cómputo mejoraría el rendimiento de una función Lambda, debes aumentar la memoria asignada a la función.
    • Despliegues seguros con Aliases: Para poder hacer rollback (volver atrás) en caso de errores tras un nuevo despliegue con impacto mínimo, cambia la aplicación para que use un alias que apunte a la versión actual. Tras desplegar el nuevo código, actualiza el alias para dirigir el 10% de los usuarios a la nueva versión. Si hay demasiados errores, envía el 100% del tráfico a la versión anterior.
    • Para evitar actualizar el endpoint de Amazon API Gateway en cada subida de código, la solución es crear alias y versiones en AWS Lambda.

    Mejores Prácticas y Troubleshooting en Lambda

    • Optimización de Código (Warm Starts): Para maximizar el rendimiento y evitar tiempos de ejecución altos, la inicialización de clientes del SDK de AWS y las conexiones a bases de datos (ej. Amazon RDS) deben declararse fuera de la función handler (en el espacio global). Esto permite reutilizar las conexiones en invocaciones subsecuentes.
    • Gestión de Dependencias (Lambda Layers): Si tu función utiliza librerías externas o personalizadas que no están en el entorno de ejecución estándar, debes instalar estas dependencias en una Lambda Layer. Esto minimiza el tiempo de cómputo y el tamaño del paquete de despliegue.
    • Troubleshooting de Rendimiento (CPU vs. Timeout): Si una función Lambda está tardando demasiado en ejecutarse por procesamiento intensivo (cuello de botella en CPU), la solución para acelerar la función es aumentar la memoria asignada. Al aumentar la memoria, AWS Lambda asigna proporcionalmente más potencia de CPU.
    • Invocaciones Asíncronas y Errores: Cuando Lambda se invoca de forma asíncrona y falla, el servicio reintenta la ejecución automáticamente dos veces. Para diagnosticar fallos persistentes en estas invocaciones, debes configurar una Dead Letter Queue (DLQ) enviando los eventos no procesados a Amazon SQS o Amazon SNS.
    • Variables de Entorno: Utilízalas para almacenar cadenas de conexión a bases de datos u otros parámetros dependientes del entorno (dev/prod). Esto evita tener que modificar o hardcodear el código fuente en cada despliegue.
    • Logs ausentes en CloudWatch: Si pruebas tu función Lambda, se ejecuta correctamente en la consola, pero no ves los logs en CloudWatch después de varios minutos, el motivo es que el Execution Role (rol de ejecución) de Lambda no tiene los permisos necesarios (logs:CreateLogGroup, logs:PutLogEvents).
    • Límites de tamaño (Deployment Package): Si la función Lambda es muy grande y el despliegue falla por tamaño (Unzipped size must be smaller than...), la solución es dividir la función en múltiples funciones Lambda más pequeñas. No intentes comprimir el ZIP dos veces.
    • Conectividad a Internet desde una VPC: Si asocias una Lambda a una subred privada de una VPC (para acceder a RDS, por ejemplo), pierde su acceso a Internet. Para restaurarlo, debes añadir un NAT Gateway en una subred pública de esa misma VPC y enrutar el tráfico de la subred privada hacia él.
    • Actualización de código desde S3: Si actualizas el código fuente subiendo un nuevo archivo .zip a S3 con el mismo nombre, Lambda no se actualizará automáticamente. Debes llamar a la API update-function-code, o bien subir el .zip con un nombre de clave (S3 Key) diferente y actualizar la plantilla.
    • Manejo de Errores Asíncronos: Si una invocación asíncrona falla tras los reintentos automáticos, debes configurar una Dead Letter Queue (DLQ) enviando los eventos no procesados a Amazon SQS o SNS para su investigación.
    • Librerías Personalizadas: Para minimizar el tiempo de cómputo y el tamaño del paquete, instala las librerías externas en una Lambda Layer para que estén disponibles para todas las funciones.
    • context objetc vs event object:
      • El event object contiene los datos (payload) enviados por el disparador (ej. el cuerpo de una petición HTTP).
      • El context object proporciona información sobre el entorno de ejecución en tiempo de ejecución, como el Request ID único (esencial para trazar logs), el tiempo restante de ejecución y el grupo de logs de CloudWatch asociado.
    • Estructura del archivo ZIP (Unable to import module): Si creas un paquete de despliegue localmente y al subirlo recibes este error, es porque comprimiste la carpeta contenedora en lugar de su contenido. Todo el código fuente y sus dependencias deben estar en la raíz (root) del archivo .zip.
    • Límites de tiempo (Long-running tasks): Si el procesamiento de un mensaje o tarea dura de media más de 15 minutos (ej. detección de fraude compleja o procesamiento de video pesado), no puedes usar Lambda. La arquitectura correcta para alta escalabilidad es enviar los mensajes a una cola Amazon SQS y configurar un grupo de Auto Scaling de instancias EC2 para procesarlos.
    • ALB como disparador: Para que un Application Load Balancer (ALB) pueda invocar una función Lambda, la función debe tener una política basada en recursos (Resource-based policy) que otorgue permisos explícitos al ALB para invocarla.

    Amazon API Gateway

    Tipos de Integración

    • Lambda Proxy Integration: API Gateway pasa toda la petición HTTP (headers, query strings, body) directamente a Lambda como un objeto JSON, y Lambda debe devolver un formato exacto que API Gateway entienda.
    • Custom Integration (Mapping Templates): Mecanismo utilizado para transformar el formato de entrada o de salida de una petición en Amazon API Gateway.
      • Velocity Template Language (VTL): Las plantillas de mapeo se escriben en VTL y son interpretadas por API Gateway para convertir la estructura de la solicitud enviada por el cliente al formato requerido por el servicio de backend de integración (por ejemplo, AWS Lambda o un servicio backend SOAP/XML heredado).
      • Extracción de Parámetros: Permiten procesar de forma dinámica las diferentes partes de la solicitud HTTP entrante —como los parámetros de query string mediante el uso de variables como $input.params('nombreDelParametro')— para construir y estructurar el objeto JSON que se traslada como evento hacia la función Lambda.

    Autorización y Control de Acceso (Authorizers)

    • Amazon Cognito User Pools: Se utiliza cuando los usuarios se autentican (AuthN) a través de la aplicación web/móvil usando directorios propios o federados (Google, Facebook, SAML) y obtienen tokens JWT que API Gateway valida de forma nativa.
    • Lambda Authorizers (Custom Authorizers): Se utiliza cuando necesitas lógica de autorización personalizada (AuthZ) o cuando debes implementar esquemas de tokens bearer que no son estándar, validar un token de terceros, o comprobar credenciales contra una tabla de Amazon DynamoDB.

    Monetización, Cuotas y Protección de Backend

    • Usage Plans (Planes de Uso) y API Keys: Permiten monetizar y limitar el consumo de peticiones asociando límites de Rate (tasa sostenida por segundo) y Burst (capacidad de ráfaga) a una o varias API Keys asignadas a clientes o inquilinos.

      No se recomienda usar alarmas de Amazon CloudWatch para aplicar limitación de acceso o throttling por cliente; la solución nativa y desacoplada son los Usage Plans.

    • Throttling en API Gateway (HTTP 429): Si un cliente excede su cuota configurada, API Gateway responde inmediatamente con 429 Too Many Requests sin invocar la función Lambda, ahorrando costes y protegiendo el límite de concurrencia.
    • JWT Authorizers vs. API Keys: Las API Keys no deben utilizarse para autenticación o autorización de seguridad; su función exclusiva es identificar al cliente para aplicar planes de uso, medición y cuotas. La autenticación se delega en Cognito User Pools o Lambda Authorizers.

    Gestión de Entornos y Optimización de Caché (Stages)

    • Reducción de Costes por Entorno (Stages): Un Stage es una referencia con nombre a un despliegue publicado de la API (ej. dev, test, prod). En arquitecturas multi-entorno, la mejor práctica económica es habilitar la caché de API Gateway únicamente cuando sea estrictamente necesario en desarrollo/pruebas, evitando pagar por capacidad de caché inactiva.
    • Invalidación de Caché por el Cliente: Cuando la caché está activa en un endpoint y un cliente necesita forzar la recuperación directa desde el backend (ignorando la caché), la solicitud HTTP debe incluir la cabecera obligatoria Cache-Control: max-age=0.

    API Gateway - Stages

    • Un stage es una referencia con nombre a un despliegue de una API para separar entornos como dev, test, prod. Es decir, un stage es una instantánea o versión de la API publicada en ese entorno.
    • Permite configurar cosas específicas del stage, por ejemplo:
      • caching
      • throttling
      • logging
      • stage variables
      • canary release para pruebas progresivas
    • Resumen: un stage no es la API en sí, sino una publicación o punto de acceso concreto de esa API.

    Integraciones Avanzadas

    • Integración con servicios Legacy (SOAP/XML):
      • Para exponer la funcionalidad de un backend XML/SOAP antiguo mediante API Gateway, se debe crear una API RESTful y utilizar la Integración Personalizada (Custom Integration).
      • Mediante el uso de Mapping Templates (plantillas de mapeo VTL), se transforma el formato JSON entrante del cliente en un formato XML válido para el backend SOAP, y viceversa en la respuesta.
    • ALB y Multi-value headers:
      • Si se utiliza un Application Load Balancer (ALB) frente a una función AWS Lambda registrada como grupo de destino (Target Group), y la arquitectura requiere enviar o procesar cabeceras HTTP con múltiples valores (multi-value headers), se debe habilitar explícitamente la opción multi-value headers en la configuración del propio ALB.

    Troubleshooting de Latencia

    • Si los usuarios experimentan alta latencia o timeouts (límite máximo de 29 segundos), debes revisar dos métricas en Amazon CloudWatch:
      • IntegrationLatency: Mide el tiempo exacto que tarda tu backend (ej. AWS Lambda) en procesar la solicitud.
      • Latency: Mide el tiempo total desde que API Gateway recibe la petición hasta que devuelve la respuesta. La diferencia entre ambas indica el retraso introducido por la propia red o por API Gateway.

    Amazon API Gateway: Códigos de Error de Troubleshooting

    Ante fallos en las peticiones HTTP gestionadas por API Gateway, los códigos de error devuelven información diagnóstica clave:

    • HTTP 429 (Too Many Requests / Throttling): Indica que se ha superado el límite de tasa de peticiones (rate limit o burst) configurado a nivel de cuenta, de etapa (stage) o mediante un plan de uso (Usage Plan).
    • HTTP 502 (Bad Gateway): Señala un error de integración en el backend. En arquitecturas con AWS Lambda (integración Proxy), ocurre cuando la función Lambda devuelve una respuesta que no cumple con el formato JSON estricto requerido por API Gateway (debe incluir statusCode, headers y body).
    • HTTP 504 (Gateway Timeout): Ocurre cuando el backend (Lambda o un servicio integrado) tarda más de 29 segundos en responder, alcanzando el límite máximo de timeout síncrono impuesto por API Gateway.

    Criterios de Selección Arquitectónica

    1. Amazon API Gateway vs. Application Load Balancer (ALB)

    Ambos operan en la Capa 7 (HTTP/HTTPS), pero resuelven necesidades distintas:

    • Elegir API Gateway cuando:
      • Se requiere un ciclo de vida completo de APIs: versionado por etapas (stages), generación de SDKs, planes de uso (Usage Plans) y monetización con API Keys.
      • Se implementan esquemas de autorización nativos de aplicación (Cognito User Pools, Lambda Authorizers, validación de JWT).
      • Se requiere soporte nativo para WebSocket APIs bidireccionales con persistencia de conexión administrada.
      • Se necesitan transformaciones de payload (JSON a XML con Mapping Templates) o validación de esquemas de solicitud antes de invocar el backend.
    • Elegir ALB cuando:
      • Se requiere balancear tráfico web estándar hacia flotas de instancias EC2 o contenedores ECS con soporte para Docker dynamic port mapping.
      • Se busca optimización de costes para volúmenes masivos de peticiones HTTP constantes sin necesidad de funciones avanzadas de API management.
      • Se requiere integración con reglas de enrutamiento basadas en cabeceras HTTP, métodos o cookies de sesión (sticky sessions).

    2. Application Load Balancer (ALB) vs. Network Load Balancer (NLB)

    • Elegir ALB: Para aplicaciones web que necesitan inspeccionar el contenido de la petición HTTP/HTTPS, descargar certificados SSL/TLS en el balanceador (TLS Termination) o dirigir el tráfico a diferentes microservicios según la ruta URL (ej. /api/v1 vs /images).
    • Elegir NLB: Para protocolos de red puros (TCP/UDP), conexiones de juegos multijugador, aplicaciones financieras que demandan millones de peticiones por segundo con latencia mínima, o cuando el cliente exige conectarse a una dirección IP estática / Elastic IP fija por Zona de Disponibilidad.

    3. AWS NAT Gateway

    • Actúa como un intermediario de traducción de direcciones de red a nivel de infraestructura.
    • Requisito Operativo: Debe desplegarse en una subred pública y asociarse a una dirección Elastic IP. Las instancias y funciones Lambda conectadas a subredes privadas deben tener una tabla de rutas cuyo destino 0.0.0.0/0 apunte hacia el ID del NAT Gateway (nat-xxxx) para obtener conectividad hacia repositorios, APIs externas o parches en Internet.

    Integración y Mensajería (Decoupling)

    Amazon SQS (Simple Queue Service)

    • Visibility Timeout: Es el tiempo que un mensaje permanece "invisible" para otros consumidores mientras un worker lo está procesando (por defecto 30 segundos). Si la tarea tarda más del tiempo establecido (ej. 5 minutos), el consumidor debe llamar a la API ChangeMessageVisibility para aumentar el tiempo; de lo contrario, el mensaje volverá a la cola y se procesará por duplicado. Al finalizar, siempre debe llamarse a DeleteMessage.
    • Delay Queues: Permite posponer la entrega de nuevos mensajes. Los mensajes se ocultan durante un tiempo configurable antes de que cualquier consumidor pueda verlos por primera vez.
    • Gestión de Mensajes de Gran Tamaño (Extended Client Library): El tamaño máximo de la carga útil (payload) de un mensaje que Amazon SQS admite nativamente es de 256 KB. Para gestionar el enrutamiento de mensajes que superan este tamaño y alcanzan hasta 2 GB, la arquitectura debe integrar Amazon S3 utilizando la biblioteca Amazon SQS Extended Client Library for Java. Esta biblioteca guarda automáticamente el contenido pesado en Amazon S3 y envía a SQS un mensaje de referencia conteniendo la ruta al objeto.
    • Configuración Avanzada en SQS
      • Visibility Timeout: Es el tiempo que un mensaje es "invisible" para otros workers. Si el proceso tarda 5 minutos pero el timeout es menor, el worker debe llamar a la API ChangeMessageVisibility para aumentarlo y evitar procesados duplicados. Al finalizar, llamar a DeleteMessage.
      • Delay Queues: Oculta los mensajes nuevos durante un tiempo configurable antes de que cualquier consumidor pueda verlos por primera vez en la cola.
      • Para aumentar la cantidad de mensajes que lee tu aplicación de golpe, usa la API ReceiveMessage y configura MaxNumberOfMessages a un valor mayor a 1 (máximo 10).

    Amazon Kinesis Data Streams

    • Shards y Orden de mensajes: Kinesis garantiza que los registros se procesan en el orden exacto (FIFO) en el que se introdujeron dentro de un Shard específico (no hay garantía de orden global entre distintos shards).
    • Troubleshooting: Si la aplicación recibe el error ProvisionedThroughputExceededException, debes aumentar el número de Shards (Resharding) e implementar exponential backoff en las llamadas a la API.
    • Garantía de Orden: Kinesis garantiza el orden exacto (FIFO) de los registros solo dentro del mismo Shard.
    • Límites: El número máximo de instancias EC2 que pueden consumir de un stream es igual al número de Shards que tenga el stream.

    AWS Step Functions

    • Manejo de Errores y Troubleshooting: Para depurar errores en las máquinas de estado de Step Functions y conservar la entrada original junto con el mensaje de error en la salida, debes utilizar la propiedad ResultPath dentro de un bloque Catch.

    Amazon CloudFront

    • Actualización de contenido en caché: Si subes una nueva versión de tu aplicación web estática (ej. CSS, JavaScript, imágenes) y los usuarios siguen viendo la versión antigua en todo el mundo, la solución para forzar la actualización es invalidar (invalidate) todos los objetos desde la caché de los Edge Locations de CloudFront.

    Swagger / OpenAPI

    Qué es

    • Swagger es un formato estándar para describir APIs REST.
    • Hoy se suele hablar de OpenAPI, que es la especificación oficial, y Swagger como la herramienta/ecosistema que la popularizó.

    Para qué se usan los ficheros Swagger

    • Definir endpoints, métodos HTTP, parámetros, cuerpos de petición y respuestas.
    • Documentar la API de forma clara para desarrolladores y clientes.
    • Generar automáticamente documentación, SDKs, stubs de cliente o servidores.
    • Facilitar la validación y el consumo de la API.
    • Integrarse con gateways de API como API Gateway, que pueden importar la especificación.

    Qué suele llevar un fichero Swagger

    • openapi: versión de la especificación.
    • info: título, versión y descripción de la API.
    • paths: rutas como /users o /orders/{id}.
    • operations: get, post, put, delete.
    • parameters, requestBody, responses, security.

    Resumen rápido

    • Un fichero Swagger/OpenAPI sirve para describir una API REST de forma estandarizada.
    • Es muy útil para documentar, validar, generar clientes y publicar APIs de forma más ordenada.

    Diferencia entre HTTP y REST

    • HTTP es el protocolo de transporte utilizado para comunicar clientes y servidores en la web.
    • REST es un estilo de arquitectura para diseñar APIs que normalmente se comunica sobre HTTP.
    • En otras palabras: HTTP define cómo se envían las peticiones y respuestas; REST define cómo deben organizarse esas peticiones para construir APIs coherentes.
    • HTTP puede usarse sin REST, por ejemplo para servir páginas web o recursos simples.
    • REST se basa en HTTP, pero añade convenciones como recursos, métodos HTTP (GET, POST, PUT, DELETE) y estados sin sesión.
