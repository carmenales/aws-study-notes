    Apuntes AWS Advance Developing

    General

    CQRS

    CQRS (Command Query Responsibility Segregation) es un patrón de diseño arquitectónico que separa las operaciones de lectura (consultas o queries) de las operaciones de escritura (comandos) en una aplicación. Permite optimizar, escalar y proteger ambas partes de forma totalmente independiente

    Conceptos Clave

    • Comandos (Commands): Son acciones que modifican el estado de los datos (crear, actualizar o eliminar) pero no devuelven información.
    • Consultas (Queries): Son operaciones que recuperan datos sin alterar el estado del sistema.

    ¿Por qué se utiliza?

    • Escalabilidad independiente: En muchos sistemas, las lecturas superan con creces a las escrituras. CQRS permite escalar la infraestructura de lectura sin necesidad de sobredimensionar la base de datos de escritura.

    • Optimización de bases de datos: Se pueden utilizar bases de datos relacionales o NoSQL optimizadas específicamente para gestionar el alto tráfico de consultas, mientras que el lado de escritura maneja de forma segura las transacciones complejas.

    • Modelo de datos simplificado: El modelo utilizado para leer datos suele ser diferente y más sencillo que el requerido para validar la lógica de negocio al escribir.

    CQRS vs Queue

    • La diferencia principal es que CQRS es un patrón de separación de responsabilidades (Lectura vs. Escritura), mientras que una arquitectura basada en colas (Queues) es un patrón de comunicación asíncrona.
    Diferencias Clave
    • Propósito principal: CQRS busca estructurar el código y los modelos de datos para optimizar lecturas y escrituras por separado. Las colas buscan desacoplar componentes, garantizar la entrega de mensajes y procesar tareas en segundo plano.
    • Manejo del tiempo: CQRS puede implementarse de forma síncrona o asíncrona. Una arquitectura basada en colas es intrínsecamente asíncrona.
    • Flujo de datos: CQRS divide la aplicación en dos caminos (comandos y consultas). Las colas gestionan el flujo de trabajo secuencial entre diferentes servicios o microservicios

    GraphQL

    • GraphQL es un lenguaje de consulta de código abierto y un tiempo de ejecución del servidor que especifica cómo deben interactuar los clientes con las interfaces de programación de aplicaciones (API).
    • GraphQL ofrece una alternativa eficiente y más flexible a la transferencia de estado representacional (REST) y a las API RESTful y resuelve algunas limitaciones de REST. Por ejemplo, proporcionar la capacidad de orientar los recursos con mayor precisión con una sola consulta.

    ¿Qué son las API GraphQL y cómo funcionan?

    Las características declarativas de obtención de datos de una arquitectura GraphQL giran en torno a varios componentes y procesos clave, cada uno de los cuales desempeña un papel único en el manejo y procesamiento de datos.

    Entre las que se encuentran:

    • Esquemas
    • Solucionadores
    • Consultas
    • Mutaciones

    CIDR

    El enrutamiento entre dominios sin clases (CIDR) es un método de asignación de direcciones IP que mejora la eficiencia del enrutamiento de datos en Internet. Cada máquina, servidor y dispositivo de usuario final que se conecta a Internet tiene asociado un número único, denominado dirección IP. Los dispositivos se encuentran y se comunican entre sí mediante estas direcciones IP. Las organizaciones utilizan el CIDR para asignar direcciones IP de manera flexible y eficiente en sus redes.

    IAM

    Permission boundaries

    • Es la posibilidad que tienes de dar permisos a usuarios para que tú lo gestiones.
    • Está limitado a un contexto.
    • No conceden permisos por sí mismas, sino que establecen el límite máximo de permisos que un usuario/rol puede llegar a tener, incluso si su política le otorga acceso total.

    Condition keys

    Las Condition Keys añaden control de acceso granular basado en contexto a las políticas de IAM, permitiendo permitir o denegar acciones según atributos específicos de la petición (como la IP origen, el uso de MFA o parámetros del propio recurso)

    AWS Elastic Beanstalk

    • AWS Elastic Beanstalk es un servicio de plataforma como servicio (PaaS) de Amazon Web Services.
    • Permite a los desarrolladores implementar y escalar aplicaciones web rápidamente cargando su código fuente, mientras que el servicio automatiza el aprovisionamiento de servidores, el balanceo de carga y el autoescalado.

    ¿Cómo funciona y qué incluye?

    • En lugar de configurar manualmente servicios como Amazon EC2, Auto Scaling o Elastic Load Balancing, Elastic Beanstalk los despliega y gestiona de forma transparente.

    Principales ventajas

    • Gestión simplificada: Tú solo te encargas de escribir y subir tu aplicación.
    • Control total: Aunque la configuración está automatizada, mantienes el control total de los recursos subyacentes y puedes modificarlos si es necesario.
    • Monitorización: Permite supervisar el estado de la aplicación y de la infraestructura fácilmente.

    Configuración y Ciclo de Vida de Aplicaciones

    • Archivos de configuración avanzada (.ebextensions): Para personalizar la infraestructura subyacente que Elastic Beanstalk aprovisiona (por ejemplo, definir una URL específica para el Health Check del balanceador de carga), las directivas deben declararse en un archivo con la extensión estricta .config. Este archivo debe ubicarse dentro de un directorio denominado .ebextensions en la raíz (root) del paquete de código fuente de la aplicación.
    • Retención de código en S3: AWS Elastic Beanstalk administra una política de ciclo de vida para las versiones de la aplicación (Application version lifecycle policy) con el fin de limitar el número máximo de versiones retenidas. Para prevenir que el proceso automático elimine los paquetes de código fuente almacenados en el bucket original de Amazon S3, la directiva Retention dentro de la configuración del ciclo de vida debe configurarse con el valor Retain source bundle in S3.

    AWS Elastic Beanstalk vs AWS CloudFormation

    La diferencia principal es que AWS Elastic Beanstalk es una Plataforma como Servicio (PaaS) centrada en desplegar aplicaciones de forma automática, mientras que AWS CloudFormation es una herramienta de Infraestructura como Código (IaC) diseñada para definir y aprovisionar cualquier recurso de AWS mediante plantillas.

    Característica AWS Elastic Beanstalk AWS CloudFormation
    Enfoque principal Centrado en la aplicación (código) Centrado en la infraestructura (recursos)
    Nivel de abstracción Alto. Oculta la complejidad de la red y los servidores Bajo. Debes definir cada componente explícitamente
    Uso de código Subes tu código fuente (.zip, .war, Docker) Creas archivos de configuración (JSON o YAML)
    Alcance Limitado a arquitecturas web estándar y microservicios Ilimitado. Puede crear bases de datos, redes, usuarios, etc.
    Público objetivo Desarrolladores que buscan rapidez Ingenieros de DevOps y administradores de sistemas

    AWS Elastic Beanstalk deployment strategies

    • All-at-once:
    • Despliega la nueva versión en todas las instancias existentes simultáneamente, in situ.
    • Reduce la capacidad a cero durante el despliegue (o genera errores) porque todas las instancias se actualizan a la vez.
    • Es la política por defecto y la más rápida, pero también la de mayor riesgo.
    • Rollback: hay que volver a desplegar la versión anterior manualmente.
    • Instancias usadas: las existentes.
    • Rolling:
    • Divide las instancias existentes en lotes y despliega lote a lote.
    • Reduce la capacidad durante el despliegue: el tamaño de la reducción es igual al tamaño del lote (las instancias del lote actual se retiran de servicio mientras se actualizan).
    • Instancias usadas: solo las existentes, en ningún momento se lanzan instancias nuevas.
    • Rollback: hay que volver a desplegar la versión anterior; puede quedar el entorno con una mezcla de versiones si falla a mitad del proceso.
    • Rolling with additional batch:
    • Igual que "Rolling", pero antes de retirar cualquier instancia de servicio, lanza un lote adicional de instancias nuevas para no perder capacidad.
    • Mantiene la capacidad total durante todo el despliegue.
    • El despliegue en sí (a partir del segundo lote) ocurre sobre las instancias existentes; el lote adicional es temporal y se termina automáticamente al finalizar el despliegue.
    • Es la opción a elegir cuando se pide explícitamente "mantener capacidad completa" + "usar las instancias existentes".
    • Coste: instancias temporales adicionales durante el despliegue.
    • Immutable:
    • Lanza una instancia EC2 completamente nueva en un Auto Scaling Group temporal, con la nueva versión ya desplegada.
    • Si pasa los health checks, lanza el resto de instancias nuevas necesarias para igualar la capacidad, las añade al balanceador, y entonces termina todas las instancias antiguas.
    • Mantiene capacidad total durante el despliegue, pero no usa las instancias existentes: construye una flota paralela completa y sustituye la anterior.
    • Rollback muy seguro y rápido: si falla, simplemente se terminan las instancias nuevas sin haber tocado las antiguas.
    • Es la opción más costosa temporalmente (duplica instancias durante el proceso) pero la más segura frente a fallos.
    • Traffic splitting:
    • Es una variante de "Immutable": lanza la flota nueva igual que en immutable, pero en lugar de mover todo el tráfico de golpe, redirige un porcentaje del tráfico a las instancias nuevas durante un periodo predefinido (canary release).
    • Si las instancias nuevas se mantienen sanas, se redirige el 100% del tráfico y se apagan las antiguas.
    • Igual que immutable: no usa las instancias existentes, construye una flota nueva.
    • Útil para detectar problemas con una fracción real de tráfico antes del cambio completo.

    Uso de Elastic Beanstalk CLI (EB CLI)

    Para gestionar despliegues de forma programática o desde línea de comandos sin usar la consola, el flujo estricto es: 1. eb init (Inicializa y configura el entorno local). 2. eb create (Crea la infraestructura base en AWS). 3. eb deploy (Despliega la nueva versión de la aplicación).

    Casos de Uso Avanzados

    • Cambio de Load Balancer (Migración a ALB): Si tu entorno usa un Classic Load Balancer y debes migrar a un Application Load Balancer (ALB), no puedes editar el entorno existente. Debes crear un nuevo entorno con el ALB configurado, desplegar tu aplicación y ejecutar una acción de Swap environment CNAMEs (Blue/Green deployment).
    • Entorno Multi-Contenedor (Docker): En AWS Elastic Beanstalk, si despliegas un entorno de múltiples contenedores de Docker (usando Amazon ECS por debajo), es obligatorio incluir un archivo llamado Dockerrun.aws.json para configurar las instancias.

    AWS OpsWorks

    AWS OpsWorks es un servicio de gestión de configuración y automatización de servidores que utiliza Chef y Puppet para automatizar cómo se configuran, despliegan y administran las instancias EC2 y los servidores en entornos on-premises.

    Trata las configuraciones y los despliegues como código (Configuration as Code), permitiendo definir recetas y manifiestos reproducibles para toda la infraestructura.

    Modalidades de AWS OpsWorks

    1. AWS OpsWorks Stacks:
    2. Permite modelar la aplicación como una estructura jerárquica: Stack (entorno global) > Layers (capas lógicas) > Instances (instancias EC2) > Apps (código fuente).
    3. Capas (Layers): Representan componentes específicos de la arquitectura (ej. capa de balanceador HAProxy/ALB, capa de servidor web NodeJS/PHP/Java, capa de base de datos MySQL). Cada capa define qué recetas de Chef ejecutar, paquetes a instalar y puertos a abrir.
    4. Tipos de Instancias en OpsWorks Stacks:
      • 24/7 Instances: Instancias de ejecución continua permanente (base de la infraestructura).
      • Time-based Instances: Se inician y apagan de forma automática según un horario programado (ideal para patrones de tráfico predecibles y reducción de costes).
      • Load-based Instances: Se escalan automáticamente hacia arriba o abajo en respuesta a métricas de carga (CPU, uso de memoria, etc.).
    5. Eventos del Ciclo de Vida (Lifecycle Events en Stacks): OpsWorks ejecuta recetas de Chef específicas en las instancias según 5 fases de ciclo de vida:
      • Setup: Se ejecuta al arrancar una instancia recién creada (instala paquetes, dependencias y servicios base).
      • Configure: Se ejecuta en todas las instancias del stack cada vez que una instancia entra o sale del estado online (ej. actualizar archivos de configuración o IPs de balanceadores).
      • Deploy: Se ejecuta cuando se despliega una nueva versión de la aplicación.
      • Undeploy: Desinstala una aplicación o revierte un despliegue anterior.
      • Shutdown: Ejecuta tareas de limpieza antes de que una instancia se apague o termine (ej. drenar peticiones activas o persistir logs).

    6. Custom Cookbooks & Berkshelf: Permite incluir cookbooks personalizados de Chef almacenados en Git o S3, gestionando dependencias de recetas con Berkshelf.

    7. AWS OpsWorks for Chef Automate:

    8. Proporciona un servidor Chef Server totalmente administrado por AWS con herramientas de Chef Automate integradas (gestión de cumplimiento con InSpec, flujos de automatización y auditoría continua).

    9. AWS OpsWorks for Puppet Enterprise:

    10. Proporciona un servidor maestro Puppet Master administrado para automatizar la gestión de configuraciones, aprovisionamiento y cumplimiento mediante Puppet Manifests.

    Claves y Palabras Clave para Exámenes (DVA-C02 & DevOps DOP-C02)

    • Palabras Clave Inmediatas: Si la pregunta del examen menciona Chef, Puppet, Cookbooks, Recipes, Berkshelf, o conceptos de Layers y Stacks, la respuesta correcta es AWS OpsWorks.
    • OpsWorks vs. Elastic Beanstalk:
    • Si el requisito es "desplegar una aplicación web con el menor esfuerzo operativo y soporte nativo para frameworks" -> Elastic Beanstalk.
    • Si el requisito es "mantener una configuración de servidores basada en recetas de Chef o manifiestos de Puppet existentes" -> AWS OpsWorks.
    • Auto-healing & Auto-scaling en OpsWorks: OpsWorks puede monitorizar instancias fallidas y reemplazarlas automáticamente (auto-healing), además de soportar instancias basadas en horario (time-based) y carga (load-based).
    • Nota de Evolución / Estado Actual: En arquitecturas modernas, AWS recomienda AWS Systems Manager (State Manager & Run Command) para gestión de configuración sin agentes de terceros, o la migración a contenedores (ECS/EKS). No obstante, en las certificaciones sigue evaluándose para distinguir estrategias de despliegue y herramientas de Configuration Management.

    Authentication, Authorization and Access Control

    API Gateways authorizes

    JWT-based authorization

    • Allows or denies requests based on token validation
    • HTTP: JWT authorizers
    • REST: Amazon Cognito user pools
    • Uses the OIDC standard JWT

    AWS IAM permissions

    • Requires a requestor with IAM credentials
    • Applies IAM policies to APIs
    • HTTP: route level
    • REST: API or method level
    • Authorizes requests the way that AWS APIs do

    Lambda authorizers

Permite que las empresas mantengan el control centralizado de sus identidades en directorios corporativos (ej. Active Directory, Okta, Azure AD) y otorguen acceso a los usuarios sin necesidad de replicar credenciales en AWS.

Define Auth Challenge: Determina el siguiente paso o reto que se presentará al cliente en función del estado actual de la autenticación. 2. Create Auth Challenge: Genera el contenido del reto (por ejemplo, un código de verificación) y lo despacha al usuario. 3. Verify Auth Challenge Response: Evalúa si la respuesta enviada por el cliente es correcta para aprobar o denegar la fase. * Pre Token Generation Trigger: Permite modificar las reclamaciones (claims) incluidas en los tokens JWT antes de que sean emitidos, facilitando la inyección dinámica de atributos de usuario, grupos o permisos personalizados. * Otros Triggers del Ciclo de Vida: Incluyen Pre Sign-up (validación previa al registro), Post Confirmation (acciones posteriores al registro exitoso), Pre Authentication y Post Authentication.

    Integración y Mensajería (Decoupling)

    SQS (Simple Queue Service)

    • Es un servicio de colas de mensajes que actúa como un amortiguador (buffer) entre los componentes de una aplicación.
    • Caso de uso en IoT: Si miles de sensores envían datos a la vez, SQS absorbe el pico de tráfico reteniendo los mensajes temporalmente. Esto evita que la base de datos o el backend colapsen, permitiendo que los consumidores (ej. funciones Lambda) procesen los datos a su propio ritmo.
    • Short Polling vs Long Polling: Para reducir costes (menos peticiones vacías) y minimizar la latencia desde que un mensaje llega a la cola hasta que el consumidor lo recibe, habilita el Long Polling estableciendo el parámetro ReceiveMessageWaitTimeSeconds a un valor mayor que 0 (ej. 20 segundos).

    SNS (Simple Notification Service)

    • Es un servicio de publicación/suscripción (Pub/Sub) de mensajes.
    • Actúa como un megáfono. Un editor envía un mensaje a un "Topic", y SNS lo distribuye instantáneamente a múltiples suscriptores (Email, SMS, HTTP/S, o colas SQS).
    • Caso de uso en IoT: Ideal para alertas en tiempo real. Si un sensor detecta una anomalía (ej. exceso de temperatura), publica en SNS para disparar alertas a los técnicos inmediatamente.

    3. Gestión de Mensajes Fallidos: Dead Letter Queues (DLQ)

    • Definición: Una cola secundaria configurada para aislar mensajes corruptos o que provocan excepciones continuas en el código (poison pills) tras agotar el número máximo de reintentos (maxReceiveCount).
    • Consejos:
      • En lugar de bloquear la cola o descartar el mensaje definitivamente, SQS lo mueve a la DLQ para análisis forense, depuración manual o re-procesamiento diferido.
      • Tanto Amazon SQS, Amazon SNS como AWS Lambda admiten la configuración de DLQs para capturar fallos de entrega e invocación asíncrona.

    Patrón Fan-out (SNS + SQS)

    • Es un patrón de arquitectura estrella en AWS. Consiste en un Topic de SNS que tiene como suscriptores a múltiples colas SQS diferentes.
    • Ventaja: Permite que un solo evento (ej. la lectura de un sensor IoT o la subida de un archivo) sea replicado y procesado por diferentes sistemas de forma paralela e independiente, sin perder mensajes.

    Arquitectura Orientada a Eventos (Event-Driven Architecture)

    La arquitectura orientada a eventos es un patrón de diseño arquitectónico basado en la producción, detección, consumo y reacción a eventos de forma desacoplada y asíncrona.

    Conceptos

    • Evento: Un cambio de estado significativo dentro de un sistema o dominio (por ejemplo, la actualización de un registro o la recepción de datos).
    • Productor de Eventos (Event Producer): El componente que detecta o genera el cambio de estado y emite un mensaje de evento hacia un intermediario o bus, sin acoplarse ni conocer la identidad de los consumidores.
    • Consumidor de Eventos (Event Consumer): El componente que se suscribe o procesa de forma asíncrona el evento emitido para ejecutar su lógica de negocio de manera autónoma.
    • Desacoplamiento Temporal y Espacial: Los productores y consumidores no necesitan estar activos al mismo tiempo (temporal) ni conocer las direcciones de red o interfaces de sus contrapartes (espacial).

    Patrones de Procesamiento: Batch vs. Event-Driven (Near-Real Time)

    En el diseño de arquitecturas sobre AWS orientadas a microservicios y bases de datos NoSQL, la elección del modelo de procesamiento determina la latencia con la que los datos analizados o derivados están disponibles para los sistemas analíticos o de negocio:

    • Procesamiento por Lotes (Batch Processing): Los datos acumulados en un almacén (como una tabla de Amazon DynamoDB) se procesan de forma diferida en intervalos programados (por ejemplo, mediante ejecuciones nocturnas). Introduce latencia significativa, ya que la información analizada no está disponible hasta la siguiente ejecución del lote.
    • Procesamiento Orientado a Eventos (Event-Driven / Near-Real Time): Los datos se procesan de forma inmediata a medida que se reciben o modifican en el origen. En AWS, este patrón se implementa desacoplando componentes mediante mecanismos nativos de captura de cambios (como Amazon DynamoDB Streams) combinados con servicios de cómputo reactivo (como AWS Lambda), eliminando la necesidad de esperar a procesos programados.

    AWS Lambda

    Cold Starts vs. Warm Starts

    • Cold Start (Arranque en frío): Ocurre cuando se invoca una función Lambda y AWS necesita crear un nuevo entorno de ejecución (descarga el código, inicia el entorno base y ejecuta el código de inicialización). Añade latencia a la respuesta.
    • Warm Start (Arranque en caliente): Ocurre cuando llega una petición y AWS reutiliza un entorno de ejecución que ya estaba inicializado e inactivo. La ejecución es casi instantánea.

    Concurrency (Concurrencia)

    Es el número de peticiones en vuelo (in-flight) que tu función Lambda está procesando al mismo tiempo.

    • Reserved Concurrency (Concurrencia Reservada):
    • Asigna una cantidad máxima de instancias concurrentes exclusivas para una función específica del total disponible en tu cuenta.
    • Doble propósito: Garantiza que esa función siempre tenga capacidad disponible (nadie se la roba) y actúa como un límite (throttle) para evitar que esa función escale infinitamente y abrume recursos downstream (como una base de datos relacional).
    • No evita los Cold Starts.
    • Provisioned Concurrency (Concurrencia Aprovisionada):
    • Pre-inicializa un número específico de entornos de ejecución para que estén listos de inmediato ("calientes").
    • Objetivo: Eliminar los Cold Starts y ofrecer latencia baja y constante para aplicaciones críticas.
    • Regla de oro (Costes): Si el tráfico mantiene ocupada esta capacidad más del 60% del tiempo, es más rentable económicamente que el modelo On-Demand puro.

    Spillover

    • Spillover significa literalmente "desbordamiento" o "exceso".
    • El "desbordamiento" es un concepto intrínseco de la gestión de la concurrencia (Provisioned vs. On-Demand) en Lambda.
    • Estrategia Híbrida: Cuando el tráfico supera tu Provisioned Concurrency, AWS Lambda maneja ese exceso (Spillover) utilizando concurrencia On-Demand estándar. Esas peticiones extra sufrirán Cold Starts, pero evitas pagar por capacidad ociosa durante las horas valle.

    Event Source Mapping (Mapeo de fuentes de eventos)

    • Es un recurso de AWS que lee automáticamente de una fuente de eventos basada en flujos o colas (como Amazon SQS, Amazon Kinesis o DynamoDB Streams) e invoca la función Lambda de forma síncrona enviándole lotes (batches) de registros.
    • Ventaja: Tú no escribes código para hacer el polling (sondeo) a la cola; AWS Lambda lo gestiona por debajo. Solo escribes la lógica para procesar el evento.

    Lambda en una VPC (Virtual Private Cloud)

    • Por defecto, las funciones Lambda se ejecutan en una VPC segura administrada por AWS con acceso directo a Internet.
    • Si tu función necesita acceder a recursos privados de tu empresa (como una base de datos RDS que no es pública), debes configurarla para que se conecte a tu VPC especificando Subredes (Subnets) y Grupos de Seguridad (Security Groups).
    • Limitación de red: Al conectar Lambda a una subred privada de tu VPC, la función pierde su acceso por defecto a Internet. Si tu código necesita salir a Internet (ej. para llamar a una API externa), la subred privada debe tener una ruta hacia un NAT Gateway público.

    Amazon DynamoDB

    Conceptos Básicos

    • Es una base de datos NoSQL de clave-valor y documentos, totalmente administrada, que ofrece un rendimiento de milisegundos de un solo dígito a cualquier escala.
    • Clave de partición (Partition Key / Hash Key): Determina en qué partición física (servidor interno) se almacenan los datos. Debe tener alta cardinalidad para distribuir bien la carga y evitar "hot partitions".
    • Clave de ordenación (Sort Key / Range Key): Es opcional. Sirve para agrupar elementos con la misma clave de partición y ordenarlos, permitiendo consultas de rango (mayor que, menor que, entre, empieza por).

    Modos de Capacidad y Cálculo de Rendimiento

    • Modo Provisionado: El administrador especifica el número exacto de lecturas y escrituras por segundo esperadas. Es la opción más eficiente en costes para patrones de tráfico predecibles y constantes.
    • Unidades de Capacidad de Escritura (WCU): 1 WCU representa 1 escritura por segundo para un elemento de hasta 1 KB. Las escrituras transaccionales (Transactional writes) tienen un coste computacional mayor y multiplican el consumo de capacidad por 2.
    • Unidades de Capacidad de Lectura (RCU): 1 RCU representa 1 lectura fuertemente consistente (Strongly Consistent) por segundo para un elemento de hasta 4 KB (o 2 lecturas eventualmente consistentes).
    • Cálculo analítico de ejemplo: Un ítem de 7 KB que requiere 3 lecturas fuertemente consistentes/seg y 10 escrituras/seg.
      • Lecturas: 7 KB se redondea al siguiente múltiplo de 4 KB (8 KB). 8 KB / 4 KB = 2 RCU por petición. 3 peticiones × 2 RCU = 6 RCU.
      • Escrituras: 7 KB se redondea al siguiente múltiplo de 1 KB (7 KB). 7 KB / 1 KB = 7 WCU por petición. 10 peticiones × 7 WCU = 70 WCU.
    • Modo On-Demand (Bajo demanda): AWS escala instantáneamente el rendimiento para acomodar el tráfico y la facturación se calcula por cada solicitud individual de lectura y escritura. Ideal para cargas de trabajo impredecibles o aplicaciones con picos pronunciados y repentinos.

    Índices Secundarios (GSI vs LSI) y Patrones de Consulta

    Los índices permiten consultar los datos de la tabla utilizando atributos alternativos a la clave principal, evitando operaciones de escaneo completo (Scan) que degradan el rendimiento y agotan la capacidad de lectura.

    Diferencias Arquitectónicas: LSI vs. GSI

    • LSI (Local Secondary Index):
      • Comparte obligatoriamente la misma clave de partición que la tabla base, pero define una clave de ordenación diferente.
      • Limitación estricta: Solo se puede definir durante la creación de la tabla base; no puede añadirse, modificarse ni eliminarse posteriormente.
      • Comparte la capacidad aprovisionada (RCU y WCU) de la tabla base.
    • GSI (Global Secondary Index):
      • Define una clave de partición diferente y, opcionalmente, una clave de ordenación diferente a las de la tabla base.
      • Flexibilidad: Se puede crear, actualizar o eliminar en cualquier momento tras la creación de la tabla.
      • Capacidad independiente: Dispone de su propia configuración de rendimiento (RCU y WCU). Si el GSI tiene capacidad de escritura sub-aprovisionada, estrangulará (throttle) las escrituras de la tabla base.

    Reglas de Unicidad y Particionado

    • Unicidad en la Tabla Base vs. GSI: Mientras que en la tabla principal la clave primaria (Partition Key o Partition + Sort Key) debe ser estrictamente única para cada ítem, en un GSI los valores de las claves no requieren ser únicos. Múltiples ítems pueden compartir la misma Partition Key en el índice (por ejemplo, agrupar múltiples jugadores bajo el mismo GameTitle).
    • Particionado Físico Interno: DynamoDB procesa el valor de la Partition Key mediante una función hash interna cuyo resultado determina la partición física exacta en la que se almacena el ítem. Los elementos que comparten la misma clave de partición se almacenan conjuntamente en la misma partición física y se ordenan por su Sort Key.

    Patrón de Consulta por Atributo Alternativo

    • Requisito de Operación Query: Una operación Query en DynamoDB exige obligatoriamente especificar un valor exacto para la Partition Key del esquema consultado.
    • Resolución de Consultas Alternativas: Si una aplicación requiere consultar datos indistintamente por dos identificadores únicos (por ejemplo, buscar un usuario por su user_id o por su email), definir email como Sort Key en la tabla base es ineficiente, ya que consultar por email sin conocer el user_id requeriría un Scan completo de todas las particiones. La solución correcta es establecer user_id como Partition Key de la tabla y crear un GSI con email como su Partition Key.

    Proyección de Atributos (Projections)

    Al definir un índice (LSI o GSI), se debe configurar la proyección de atributos para determinar qué datos se copian de la tabla base al índice: * KEYS_ONLY: Solo proyecta las claves de la tabla base y las claves del índice (menor consumo de almacenamiento y capacidad). * INCLUDE: Proyecta las claves más una lista específica de atributos adicionales requeridos frecuentemente por las consultas. * ALL: Proyecta todos los atributos de la tabla base al índice (mayor consumo de almacenamiento y WCUs duplicadas).

    DAX (DynamoDB Accelerator)

    • Es un clúster de caché en memoria totalmente administrado, de alta disponibilidad y diseñado específicamente para DynamoDB.
    • Acelera el rendimiento de lectura reduciendo la latencia de milisegundos a microsegundos.
    • Es compatible con la API de DynamoDB, lo que significa que los desarrolladores no necesitan reescribir la lógica de la aplicación para implementarlo.
    • Es la solución ideal para aplicaciones con cargas de lectura extremadamente intensivas o para aliviar el tráfico sobre una misma clave de partición muy solicitada (hot key).

    Operaciones Avanzadas y Gestión de Datos

    • Time To Live (TTL): Para eliminar registros antiguos de forma automática de DynamoDB, debes añadir un nuevo atributo de tipo numérico (Number) que contenga un timestamp. Luego, configuras la tabla con un TTL que haga referencia a ese nuevo atributo.
    • Consistencia y Rendimiento: Las lecturas fuertemente consistentes (Strongly Consistent Reads) utilizan más capacidad de rendimiento (throughput) que las lecturas eventualmente consistentes.
    • Transacciones: Si tu aplicación necesita realizar cambios coordinados de "todo o nada" en múltiples ítems de DynamoDB, debes usar la operación TransactWriteItems para agrupar los cambios.
    • Operaciones en lote: Para permitir la recuperación de múltiples ítems de una tabla en una sola llamada a la API, debes usar la operación BatchGetItem.
    • Lecturas Fuertemente Consistentes por API: Por defecto, las consultas a DynamoDB son eventualmente consistentes. Si un requerimiento exige consistencia fuerte en el código (para no recuperar datos viejos), debes configurar explícitamente el parámetro ConsistentRead a true al llamar a las APIs GetItem o Query.
    • Desacoplamiento con DynamoDB Streams: En arquitecturas de microservicios, si el "Servicio A" tiene su propia tabla DynamoDB y el "Servicio B" necesita enterarse en tiempo real de los cambios (ej. Servicio de Cuentas y Servicio de Pagos), el patrón más simple y fiable es habilitar Amazon DynamoDB Streams en la tabla A para capturar las modificaciones y enviar los eventos al Servicio B.

    CI/CD (Developer Tools)

    AWS Serverless Application Model (AWS SAM)

    AWS SAM es un framework de código abierto para compilar aplicaciones sin servidor (serverless). Es una extensión de AWS CloudFormation, por lo que cualquier plantilla de SAM requiere obligatoriamente la declaración Transform: AWS::Serverless-2016-10-31 en la raíz del documento para que CloudFormation interprete la sintaxis simplificada y construya los recursos subyacentes.

    Estructura y Secciones de la Plantilla

    • Globals: Permite definir configuraciones comunes que se reutilizan en múltiples recursos dentro de la plantilla. Si varias funciones sin servidor comparten propiedades como Runtime, Memory, VpcConfig, Environment o Cors, se declaran una única vez en la sección Globals y todos los recursos AWS::Serverless::Function heredan dichos valores. Esto reduce la duplicación de código y facilita el mantenimiento a escala.
    • Parameters: Permite inyectar valores dinámicos en la plantilla en el momento de la ejecución o despliegue (por ejemplo, para definir identificadores de entorno como dev o prod), proporcionando la flexibilidad necesaria para reutilizar la misma plantilla en diferentes contextos o cuentas.

    Gestión de Permisos

    • SAM Policy Templates: Son plantillas de políticas de IAM predefinidas por AWS que permiten aplicar el principio de privilegio mínimo a las funciones Lambda sin necesidad de redactar documentos JSON completos. Se asignan a través de la propiedad Policies del recurso (ej. DynamoDBCrudPolicy, S3ReadPolicy, SQSPollerPolicy), limitando el acceso de forma estricta y segura a los recursos especificados.

    Comandos de la CLI de AWS SAM

    Para el ciclo de desarrollo, pruebas locales y despliegue programático, el flujo de trabajo requiere el uso de comandos específicos de la CLI de AWS SAM:

    • sam init: Inicializa un nuevo proyecto de AWS SAM desde plantillas predefinidas o desde un tipo de aplicación concreto, generando la estructura base del repositorio y los archivos necesarios para empezar a desarrollar.
    • sam build: Procesa la plantilla de AWS SAM, el código de la aplicación y cualquier dependencia, compilando los artefactos de construcción localmente para prepararlos para el despliegue.
    • sam validate: Valida la sintaxis y la estructura de la plantilla de AWS SAM antes de desplegarla, ayudando a detectar errores de configuración o incompatibilidades en la definición de recursos.
    • sam local invoke: Ejecuta y prueba una función Lambda localmente utilizando una imagen de contenedor Docker de código abierto que simula de forma exacta el entorno de ejecución de AWS Lambda. Facilita la depuración local, la inyección de eventos de prueba y la revisión de registros antes de afectar la infraestructura en la nube.
    • sam sync: Sincroniza automáticamente los cambios del código local con el entorno de AWS en tiempo casi real. Omite la ejecución estándar del ciclo completo de AWS CloudFormation para acelerar la iteración y el ciclo de retroalimentación de código durante la fase de desarrollo.
    • sam package (o aws cloudformation package): Empaqueta los artefactos de la aplicación, los sube a un bucket de Amazon S3 y genera un archivo de plantilla modificado que hace referencia a la ubicación exacta de estos artefactos en S3.
    • sam deploy (o aws cloudformation deploy): Despliega la aplicación sin servidor utilizando la plantilla empaquetada. Crea o actualiza una pila (Stack) de AWS CloudFormation en la cuenta destino con los recursos definidos.
    • sam publish: Publica una versión del artefacto de la aplicación en el registro de aplicaciones de AWS Serverless Application Repository (SAR), permitiendo compartir o reutilizar la aplicación como un paquete desplegable reutilizable.

    AWS CodeCommit

    • Es un servicio de control de código fuente administrado, seguro y de alta escalabilidad que aloja repositorios Git privados.
    • Integración IAM: A diferencia de un Git autogestionado, CodeCommit se integra de forma nativa con IAM, permitiendo controlar el acceso a los repositorios a nivel de usuario y asignar permisos granulares (por ejemplo, restringir quién puede hacer push a la rama main).
    • Cifrado: Los repositorios se cifran automáticamente en reposo (con AWS KMS) y en tránsito.
    • Clonación HTTPS: Antes de clonar un repositorio de CodeCommit sobre HTTPS, la forma más segura y recomendada de autenticarse es configurar el Git credential helper para que utilice el perfil de credenciales de AWS de la máquina local.

    AWS CodeBuild

    • Es un servicio de integración continua totalmente administrado que compila código fuente, ejecuta pruebas y produce paquetes de software listos para su despliegue.
    • No es necesario aprovisionar, administrar ni escalar sus propios servidores de compilación; AWS escala los contenedores de compilación automáticamente.
    • El archivo clave (buildspec.yml): Es un archivo en formato YAML que debes colocar en el directorio raíz de tu código fuente. Contiene las instrucciones y comandos que CodeBuild usará para ejecutar la compilación (dividido en fases como install, pre_build, build, post_build).
    • Troubleshooting de Compilación: Si un proyecto de CodeBuild falla tras un cambio en el código fuente, el lugar correcto para identificar la causa raíz es revisar los Build Logs (registros de compilación) de la fase fallida en el historial de compilación (Build History) de CodeBuild.
    • Variables de Entorno Masivas: Si el comando falla porque la suma de las variables de entorno supera el límite máximo de caracteres permitido, la solución recomendada es guardar esas variables en AWS Systems Manager Parameter Store.
    • Ejecución de Pruebas Unitarias: En un pipeline de CI/CD (con AWS CodePipeline), las pruebas unitarias siempre deben ejecutarse actualizando el archivo de especificación de AWS CodeBuild (buildspec.yml) para incluir una fase de tests, antes de pasar el artefacto a la fase de pruebas o despliegue.

    AWS CodeDeploy

    • Es un servicio de despliegue totalmente administrado que automatiza las implementaciones de software en una variedad de servicios de computación, como Amazon EC2, AWS Fargate, AWS Lambda y servidores on-premises.
    • El archivo clave (appspec.yml):
    • Archivo YAML (o JSON) que define cómo CodeDeploy debe ejecutar el despliegue y gestionar el ciclo de vida del enrutamiento del tráfico (los hooks como BeforeInstall, AfterInstall, ApplicationStart).
    • Para que AWS CodeDeploy funcione correctamente, este archivo debe colocarse obligatoriamente en el directorio raíz (root) de la estructura del código fuente de la aplicación.
    • Tipos y configuraciones de despliegue:
    • In-place deployment (Despliegue in situ): La aplicación en cada instancia del grupo de despliegue se detiene, se instala la última revisión y se inicia y valida la nueva versión. (No soportado para AWS Lambda ni Amazon ECS).
    • Blue/Green deployment (Despliegue azul/verde): El tráfico se redirige desde el entorno original (azul) hacia un entorno de reemplazo idéntico (verde) que tiene la nueva versión de la aplicación. Es el más seguro porque permite un rollback (vuelta atrás) instantáneo simplemente devolviendo el tráfico al entorno original.
    • Canary deployment (Despliegue Canary): El tráfico se desplaza a la nueva versión en dos incrementos. Primero, se envía una pequeña porción del tráfico (por ejemplo, el 10%) a la nueva versión. Tras un periodo de tiempo especificado de espera y evaluación (por ejemplo, 10 minutos), el porcentaje de tráfico restante (90%) se redirige de golpe a la nueva versión. Minimiza el impacto en los usuarios si la nueva versión tiene errores.
    • Linear deployment (Despliegue Lineal): El tráfico se redirige a la nueva versión en incrementos iguales y regulares, dejando un tiempo específico entre cada incremento (por ejemplo, enviar un 10% más de tráfico cada 5 minutos hasta llegar al 100%).
    • All-at-once (Todo a la vez): Todo el tráfico se redirige de la versión original a la nueva versión de forma simultánea. Es el más rápido, pero el más arriesgado si hay fallos.
    • Orden de Lifecycle Hooks: Para un despliegue de tipo in-place (in situ), el orden de ejecución correcto de los hooks en el archivo appspec.yml es:
      1. ApplicationStop
      2. BeforeInstall
      3. AfterInstall
      4. ApplicationStart
    • Despliegues Híbridos: Si necesitas automatizar el despliegue de un paquete de software tanto en instancias Amazon EC2 como en servidores virtuales on-premises, AWS CodeDeploy es la herramienta adecuada. Deberás subir tu bundle a Amazon S3 y configurarlo como origen.

    Estrategias de Desplazamiento de Tráfico (Traffic Shifting) en Serverless

    En entornos Serverless (como AWS Lambda), dado que no hay servidores en los que instalar software gradualmente, AWS CodeDeploy utiliza el desplazamiento de tráfico (mediante Aliases y pesos). Dirige un porcentaje exacto de las invocaciones a la nueva versión mientras el resto sigue en la versión antigua.

    Las dos estrategias principales para este despliegue gradual son:

    • Canary deployment (Despliegue Canary): El desplazamiento de tráfico se hace en solo dos pasos. Primero, envía una pequeña porción del tráfico (ej. 10%) a la nueva versión para probarla. Tras un periodo de evaluación (ej. 10 minutos) para verificar que no hay errores, el 90% restante del tráfico se redirige de golpe en un segundo y último paso.
    • Linear deployment (Despliegue Lineal): El desplazamiento de tráfico se hace en múltiples pasos iguales y escalonados. El tráfico se redirige a la nueva versión en incrementos regulares, dejando un tiempo de evaluación entre cada incremento (ej. 10% de tráfico cada 5 minutos hasta alcanzar el 100%).

    Automatización y Pruebas Continuas con AWS SAM y CodeDeploy

    Pruebas a lo largo del Pipeline (Best Practice) Una canalización (pipeline) automatizada y bien estructurada debe incluir validaciones progresivas en cada etapa para garantizar que los errores se detecten antes de llegar a producción: - Fase de Build: Ejecución de análisis estático de código (linting/sintaxis), pruebas unitarias y compilación (usualmente con CodeBuild). - Fase de Testing: Despliegue de la aplicación en un entorno de pruebas para ejecutar pruebas de integración aisladas (utilizando mocks o stubs para simular otros servicios). - Fase de Staging: Pruebas de integración contra servicios reales (API tests). Es el lugar ideal para incluir una etapa de Aprobación Manual (QA sign-off). - Fase de Producción: Despliegue gradual empleando estrategias Canary o Linear, validado mediante pruebas automatizadas de tráfico.

    Despliegues Seguros (Safe Deployments) en AWS SAM AWS SAM permite automatizar los despliegues graduales de las funciones Lambda integrando las configuraciones de AWS CodeDeploy directamente en la plantilla de infraestructura (mediante la propiedad DeploymentPreference).

    • Tipos de despliegue nativos: Puedes configurar la plantilla para que la actualización de la Lambda utilice estrategias Canary o Linear para realizar pruebas Blue/Green de forma automática.
    • Rollback Automático: Si alguna de las pruebas falla durante el proceso de despliegue gradual, el pipeline se detiene automáticamente y revierte (rollback) el tráfico a la versión anterior para proteger el entorno de producción.
    • Traffic Hooks (Funciones de validación): AWS SAM permite especificar funciones Lambda auxiliares que CodeDeploy invocará automáticamente para testear el despliegue:
    • PreTraffic Hook: Se ejecuta antes de que el tráfico de los usuarios empiece a ser redirigido a la nueva versión. Sirve para comprobar la salud (health check) de la nueva función. Si esta prueba falla, el despliegue se aborta instantáneamente.
    • PostTraffic Hook: Se ejecuta después de que el 100% del tráfico ya se ha desplazado a la nueva versión. Se utiliza para ejecutar pruebas de integración de extremo a extremo (E2E) finales o enviar métricas/notificaciones de éxito.

    Lifecycle Event Hooks para Amazon ECS (Despliegues Blue/Green)

    En despliegues Blue/Green de Amazon ECS administrados por CodeDeploy, cada hook ejecuta una función AWS Lambda (una por evento) para validar el estado del despliegue. Si la función Lambda reporta un fallo (Failed mediante la API PutLifecycleEventHookExecutionStatus), CodeDeploy aborta el proceso y realiza un rollback automático.

    El orden secuencial de ejecución de los hooks en ECS es:

    1. BeforeInstall:
    2. Se ejecuta antes de que se cree el conjunto de tareas de reemplazo (replacement task set).
    3. El Target Group original y el test listener (si existe) están asociados al task set original.
    4. Nota: En este punto no es posible realizar un rollback porque el nuevo task set aún no existe (el despliegue simplemente se cancela).
    5. AfterInstall:
    6. Se ejecuta después de crear el replacement task set y asociarle uno de los Target Groups (el de reemplazo).
    7. Permite verificar que las tareas arrancaron y superaron los health checks del contenedor antes de abrir tráfico de pruebas.
    8. Si falla, puede desencadenar un rollback.
    9. AfterAllowTestTraffic:
    10. Se ejecuta después de que el Test Listener (puerto de pruebas del balanceador) empieza a enviar tráfico al replacement task set.
    11. Ideal para ejecutar pruebas de integración, tests de API o validaciones automáticas de QA sin afectar a los usuarios reales.
    12. Si las pruebas fallan, se dispara un rollback.
    13. BeforeAllowTraffic:
    14. Se ejecuta después de asociar el segundo Target Group al replacement task set, pero antes de desplazar el tráfico de producción hacia él.
    15. Es la última validación (ej. precalentamiento de caché, comprobación de alarmas) antes de que los usuarios finales reciban tráfico de la nueva versión.
    16. Si falla, desencadena un rollback.
    17. AfterAllowTraffic:
    18. Se ejecuta después de que el tráfico de producción ha sido redirigido (total o parcialmente vía Canary/Linear) al replacement task set.
    19. Permite monitorear métricas en tiempo real (tasas de error 5xx, latencia) y enviar notificaciones.
    20. Si falla, desencadena un rollback devolviendo el tráfico al task set original.

    AWS CodePipeline

    • Es un servicio de entrega continua totalmente administrado que ayuda a automatizar los canales de publicación (pipelines) para lograr actualizaciones de aplicaciones e infraestructuras rápidas y fiables.
    • Orquestación: CodePipeline no compila ni despliega por sí mismo; orquesta a los demás servicios (extrae el código de CodeCommit, manda compilar a CodeBuild y manda desplegar a CodeDeploy).
    • Artifacts (Artefactos): A medida que el código pasa de una etapa (stage) a otra, CodePipeline guarda y transfiere los archivos generados utilizando un bucket de Amazon S3 designado como almacén de artefactos.
    • Manual Approvals (Aprobaciones manuales): Permite añadir una etapa de revisión manual donde el pipeline se pausa hasta que una persona con los permisos de IAM adecuados apruebe o rechace la transición al siguiente entorno (muy usado antes de desplegar en Producción).
    • Si el flujo requiere que una persona apruebe el código antes de desplegar en producción, añade una acción de aprobación (approval action) a la etapa correspondiente.
    • Configura esta acción de aprobación para que publique en un topic de Amazon SNS. Esto detendrá la ejecución del pipeline a la espera de la aprobación.

    AWS CloudFormation (Exportación entre Stacks)

    • Para hacer referencia a un recurso (ej. una VPC o S3 Bucket) creado en una plantilla de infraestructura desde otra plantilla de aplicación, usa la declaración Export en la sección Outputs de la primera plantilla, y luego usa la función Fn::ImportValue en la segunda.

    Resolución de Problemas (Troubleshooting) y Configuración Estricta

    • Ubicación de AppSpec en AWS CodeDeploy: El motor de implementación requiere obligatoriamente que el archivo de especificación appspec.yml se encuentre ubicado en el directorio raíz (root) de la estructura del código fuente de la aplicación.
    • Límites de Variables en AWS CodeBuild: Si un proyecto de compilación falla debido a que la longitud combinada de todas las variables de entorno definidas supera el límite de caracteres impuesto por el servicio, la solución recomendada es eliminar dichas variables del proyecto y almacenarlas como pares clave-valor dentro de AWS Systems Manager Parameter Store.
    • Identificación de Fallos de Compilación: Si un cambio reciente en el repositorio de origen provoca un error de compilación en AWS CodeBuild, la causa raíz debe auditarse revisando los registros de construcción (Build logs) correspondientes a la fase fallida dentro del historial de compilación (Build history) del proyecto.
    • Comportamiento de Rollback Automático en CodeDeploy: Durante una implementación in-situ (in-place) sobre instancias EC2 con los rollbacks automáticos habilitados, si el despliegue falla por una regresión en el código, CodeDeploy no restaura instantáneas (snapshots). El servicio vuelve a desplegar automáticamente la última versión funcional (last known good deployment) ejecutándola como una nueva implementación con un ID de despliegue completamente nuevo.

    CI/CD Avanzado (Despliegues Multi-Cuenta y Orquestación)

    Despliegues Multi-Cuenta (Cross-Account Deployments en CodePipeline)

    Para centralizar la integración y entrega continua en una cuenta centralizada (Tooling Account) y realizar despliegues automatizados en cuentas aisladas (como Staging o Production): - Roles de Acceso Cruzado (Cross-Account Roles): Se configura un rol de IAM en la cuenta de destino que establece una relación de confianza (Trust Policy) con el rol de servicio de CodePipeline de la cuenta central. - Flujo de Ejecución: Durante la fase de despliegue, CodePipeline utiliza operaciones de AWS STS (AssumeRole) para adquirir credenciales de seguridad temporales, permitiendo aprovisionar o actualizar recursos en la cuenta de destino sin utilizar claves de acceso permanentes.

    Acciones Personalizadas (Custom Actions) en CodePipeline

    • Cuando las acciones predeterminadas (como AWS CodeBuild, AWS CodeDeploy o Amazon S3) no satisfacen los requisitos del flujo de trabajo, se pueden implementar Custom Actions.
    • Permiten integrar herramientas externas o procesos personalizados (ej. análisis estático de seguridad de terceros) asociando la acción a una función de AWS Lambda o a un servicio web registrado como proveedor de acciones personalizadas.

    Automatización de Pipelines con Amazon EventBridge

    • Monitoreo de Cambios de Estado: Amazon EventBridge intercepta de forma nativa los eventos generados por las herramientas de desarrollo (ej. fallos en compilaciones de CodeBuild, cambios de estado en CodePipeline o eventos de despliegue en CodeDeploy).
    • Acciones Automatizadas: Permite configurar reglas (Rules) basadas en patrones de eventos para disparar acciones reactivas de manera asíncrona, tales como el envío de alertas operativas mediante Amazon SNS o la ejecución de rutinas de diagnóstico con AWS Lambda.

    Orquestación:

    AWS Step Functions: Patrones y Gestión de Estado

    AWS Step Functions es el servicio de orquestación serverless basado en máquinas de estado definidas en JSON o YAML mediante el Lenguaje de Estados de Amazon (Amazon States Language). Permite coordinar servicios de AWS como AWS Lambda o Amazon DynamoDB en flujos secuenciales o paralelos.

    Standard vs. Express Workflows

    • Standard Workflows:
    • Diseñados para flujos de trabajo de larga duración (con un límite de ejecución de hasta 1 año).
    • Mantienen un historial de ejecución detallado y persistente, permitiendo la auditoría visual completa de cada paso en la consola de AWS.
    • Se facturan en función del número de transiciones de estado ejecutadas.
    • Indicados para procesos críticos, transacciones financieras o flujos que requieren intervención humana (human-in-the-loop).
    • Express Workflows:
    • Diseñados para procesamiento de alto volumen y corta duración (con un límite máximo de 5 minutos por ejecución).
    • Optimizados para arquitecturas orientadas a eventos de alta frecuencia, ingesta de datos o microservicios síncronos.
    • Los registros de eventos y ejecución se transmiten directamente a Amazon CloudWatch Logs en lugar de persistir el historial en la consola del servicio.
    • Se facturan por número de solicitudes, duración y consumo de recursos de memoria.

    Patrón de Integración: Wait for Callback (TaskToken)

    • Se utiliza cuando una tarea en la máquina de estado necesita suspender su ejecución y aguardar a que un proceso externo (sistemas on-premises, operadores humanos o servicios de terceros) complete una acción y emita una respuesta explícita.
    • Al configurar la tarea con el sufijo .waitForTaskToken, Step Functions genera un identificador único (TaskToken) que se incluye en la carga útil (payload) enviada a través de un servicio de mensajería (ej. Amazon SQS o Amazon SNS).
    • La ejecución del flujo permanece en pausa indefinida hasta que el componente externo recupera dicho TaskToken y ejecuta las llamadas a la API SendTaskSuccess o SendTaskFailure.

    Manejo de Errores: Catch y Retry

    • Retry: Permite reintentar de forma automática la ejecución de un estado cuando se produce un error específico (ErrorEquals). Sus parámetros principales son:
    • IntervalSeconds: Tiempo de espera inicial previo al primer reintento.
    • BackoffRate: Factor multiplicador que incrementa de forma exponencial el intervalo de espera entre reintentos.
    • MaxAttempts: Límite máximo de intentos permitidos antes de declarar el fallo definitivo.
    • Catch: Permite capturar errores que han agotado los reintentos configurados o que no disponen de reglas de reintento, desviando la ejecución hacia un estado de control de errores alternativo.
    • ResultPath: Propiedad que permite conservar simultáneamente la entrada original del estado y el mensaje de error en la salida, evitando la pérdida de contexto durante el proceso de depuración.

    Step Functions vs Simple Workflow Service (SWF)

    • AWS Step Functions: Es el orquestador serverless recomendado. Se define con máquinas de estado (JSON/YAML). Ideal para coordinar lambdas secuenciales o en paralelo.
    • Amazon SWF (Simple Workflow Service): Es un servicio heredado (legacy). Su característica distintiva en el examen es que la lógica está dividida entre Workers (los que hacen el trabajo) y Deciders (los que deciden qué tarea va después). Si una pregunta menciona deciders y workers, se refiere a SWF.

    Entornos Multi-Cuenta y Operaciones Globales

    AWS Organizations y Organizational Units (OUs)

    AWS Organizations es un servicio de gestión de cuentas que permite centralizar la administración de múltiples cuentas AWS bajo una única estructura jerárquica. - Management Account (Cuenta de Gestión): Cuenta central responsable de crear la organización, administrar la facturación consolidada y gestionar los métodos de pago. - Organizational Units (OUs - Unidades Organizativas): Agrupaciones lógicas de cuentas dentro de una organización (ej. Security OU, Workloads OU, Sandbox OU). Permiten aplicar controles de gobernanza heredando políticas de manera jerárquica. - Service Control Policies (SCPs): Políticas JSON adjuntas a la cuenta de gestión, a una OU o a una cuenta individual que establecen los permisos máximos disponibles para todas las identidades (usuarios y roles) de las cuentas miembro. Actúan como un límite estricto de control: una SCP de tipo Deny anula cualquier permiso otorgado por IAM en las cuentas subordinadas.

    AWS Control Tower

    AWS Control Tower automatiza la configuración de un entorno multi-cuenta seguro y estandarizado (Landing Zone) alineado con el marco Well-Architected Framework. - Guardrails: Reglas de gobernanza aplicadas de forma continua en toda la organización: - Preventative Guardrails: Implementados mediante SCPs para bloquear acciones que violen las políticas de seguridad. - Detective Guardrails: Implementados mediante reglas de AWS Config y eventos en Amazon EventBridge para identificar desviaciones de cumplimiento. - Account Factory: Automatiza el aprovisionamiento de nuevas cuentas estandarizadas con redes, seguridad y políticas preconfiguradas.

    AWS CloudFormation StackSets

    Permite desplegar, actualizar o eliminar pilas (stacks) de CloudFormation de forma simultánea en múltiples cuentas de AWS y múltiples regiones desde una única plantilla centralizada. - Modos de Permisos: - Self-managed permissions: Requiere la creación manual de roles IAM específicos (cloudformation-stackset-execution-role) en cada cuenta de destino para autorizar a la cuenta administradora. - Service-managed permissions (Recomendado): Integrado de forma nativa con AWS Organizations. Permite automatizar el despliegue en todas las cuentas actuales y futuras de una organización o de una OU específica sin configurar roles manualmente en cada cuenta miembro. - Parámetros de Operación: Permite definir la concurrencia máxima de despliegue y el porcentaje de tolerancia a fallos (Failure Tolerance) para controlar la propagación de los cambios a escala global.

    AWS Resource Access Manager (AWS RAM)

    Servicio que permite compartir recursos de AWS de forma segura entre cuentas de AWS, ya sea dentro de una Organización de AWS (o unidad organizativa OU), o con cuentas individuales externas e identidades de IAM.

    Elimina la necesidad de duplicar recursos en cada cuenta, reduciendo significativamente los costes de infraestructura y la sobrecarga operativa.

    ¿Cómo funciona un Resource Share?

    1. Creación del Recurso Compartido (Resource Share): La cuenta propietaria (Resource Owner) selecciona los recursos que desea compartir.
    2. Asignación de Permisos (Managed Permissions): Define qué acciones exactas pueden realizar las cuentas consumidoras sobre el recurso.
    3. Especificación de Destinatarios (Principals): Se pueden especificar cuentas de AWS individuales, IDs de OUs o la Organización completa.
    4. Mecanismo de Aceptación:
    5. Dentro de AWS Organizations: Si el uso compartido está habilitado a nivel de organización, los recursos compartidos se aceptan automáticamente y están disponibles de inmediato sin enviar invitaciones manuales.
    6. Fuera de la Organización (Cuentas individuales): La cuenta de destino recibe una invitación en AWS RAM que debe ser aceptada explícitamente antes de acceder a los recursos.

    Recursos Principales y Casos de Uso Clave (Examen)

    • VPC Subnets (VPC Sharing / Subredes Compartidas):
    • Permite a una cuenta central de red compartir subnets de una VPC con otras cuentas miembro de la organización.
    • Las cuentas consumidoras pueden desplegar sus recursos de cómputo (instancias EC2, tareas ECS, funciones Lambda en VPC, bases de datos RDS) dentro de las mismas subnets compartidas.
    • Reglas de Seguridad y Aislamiento:
      • Los usuarios de una cuenta solo pueden ver, modificar y gestionar sus propios recursos. No pueden ver ni modificar recursos creados por otras cuentas.
      • Los Security Groups pertenecen a cada cuenta; los recursos de una cuenta pueden referenciar Security Groups de otra cuenta usando el formato AccountID/sg-xxxxxx.
      • La cuenta propietaria de la VPC retiene el control exclusivo sobre la VPC, subnets, Route Tables, Internet Gateways, NAT Gateways y Network ACLs (NACLs).
    • AWS Transit Gateway: Compartir un Transit Gateway centralizado entre todas las cuentas de la organización para interconectar múltiples VPCs y conexiones on-premises sin duplicar pasarelas.
    • Route 53 Resolver Rules: Compartir reglas de reenvío DNS (DNS Forwarding Rules) entre múltiples cuentas para resolución de nombres híbrida u hospedada.
    • AWS License Manager: Compartir licencias de software comerciales entre cuentas para controlar cuotas y evitar infracciones de licenciamiento.
    • Amazon Aurora DB Clusters: Compartir snapshots de bases de datos para clonación rápida entre cuentas.

    [!TIP] Diferencia Arquitectónica Clave para el Examen: - VPC Peering / Transit Gateway: Conectan VPCs distintas y separadas entre sí para permitir tráfico IP entre ellas. - AWS RAM (VPC Sharing): Permite que múltiples cuentas compartan las mismas subredes dentro de una única VPC común, centralizando la gestión de red (un solo NAT Gateway, una sola tabla de rutas) y reduciendo costes de transferencia entre cuentas.

    Gestión de Gobernanza y Automatización (AWS Systems Manager y AWS Config)

    AWS Systems Manager (SSM)

    Suite de herramientas centralizada para el control operativo, la gestión de configuración y la automatización de recursos en la nube y en entornos on-premises.

    • Parameter Store: Almacenamiento jerárquico de pares clave-valor para datos de configuración de aplicaciones y secretos básicos. Organiza los parámetros mediante rutas (ej. /prod/database/password) y soporta cifrado mediante claves de AWS KMS (SecureString).
    • Session Manager: Capacidad de gestión interactiva de nodos (instancias EC2 y servidores on-premises) mediante un shell basado en navegador o mediante la AWS CLI. Elimina la necesidad de abrir puertos de red entrantes (como SSH en el puerto 22 o RDP en el 3389), gestionar claves SSH o desplegar hosts bastión (jump boxes), ya que el tráfico se canaliza de forma segura a través de HTTPS mediante un agente instalado en la instancia.
    • Patch Manager: Automatiza el proceso de aplicación de parches de sistemas operativos y software en flotas masivas de instancias mediante líneas de referencia (patch baselines) y calendarios de ejecución (maintenance windows).
    • Automation Documents: Permite definir flujos de trabajo basados en código (YAML o JSON) para automatizar tareas rutinarias de administración, diagnóstico y remediación operativa a escala.

    AWS Config

    Servicio de evaluación, auditoría y supervisión continua de las configuraciones de los recursos de AWS.

    • Historial de Configuración: Registra los cambios de configuración de los recursos de la cuenta, permitiendo evaluar el estado actual frente a un punto específico del pasado.
    • AWS Config Rules: Reglas personalizadas o gestionadas que evalúan si las configuraciones de los recursos de AWS cumplen con las directrices de seguridad y gobernanza corporativa.
    • Conformance Packs (Paquetes de conformidad): Colecciones de reglas de AWS Config y documentos de automatización empaquetados como una única entidad para simplificar la gestión del cumplimiento frente a normativas específicas (ej. PCI-DSS, HIPAA).
    • Remediación Automática: Permite asociar una regla de AWS Config que detecte un recurso no conforme a un documento de automatización de AWS Systems Manager (SSM Automation). Esto permite corregir de forma automática y en tiempo real las desviaciones de seguridad en la infraestructura.

    Gestión de Configuración y Automatización (AWS Systems Manager)

    AWS Systems Manager Parameter Store

    • Almacenamiento de Secretos y Configuración: Permite almacenar datos de configuración de aplicaciones y credenciales (como contraseñas de bases de datos o claves de API) de forma centralizada en formato de pares clave-valor.
    • Resolución de Límites en CI/CD: Se utiliza como solución recomendada cuando los proyectos de compilación en AWS CodeBuild fallan debido a que la longitud combinada de las variables de entorno supera el límite máximo de caracteres permitido.
    • Acceso Seguro desde Instancias: Permite que las aplicaciones desplegadas en instancias Amazon EC2 recuperen credenciales y parámetros de forma programática utilizando los permisos otorgados por un rol de IAM, evitando almacenar claves de acceso estáticas en el código fuente.

    Estrategias de Recuperación ante Desastres (Disaster Recovery - DR) y Enrutamiento

    Conceptos Fundamentales de Resiliencia

    • Recovery Point Objective (RPO): Es la cantidad máxima aceptable de pérdida de datos medida en el tiempo, derivada del momento en que se produce el desastre hasta la última copia de seguridad o sincronización disponible.
    • Recovery Time Objective (RTO): Es el tiempo máximo aceptable que un sistema puede permanecer inactivo o inaccesible después de que ocurre una interrupción del servicio.

    Estrategias de Disaster Recovery en AWS

    Las arquitecturas de alta disponibilidad y recuperación se clasifican según su complejidad, coste y los tiempos de recuperación (RTO/RPO):

    1. Backup and Restore (Copia de seguridad y restauración):
    2. Funcionamiento: Los datos se respaldan de forma periódica (ej. mediante snapshots de Amazon EBS o copias en Amazon S3/Glacier) hacia una región de respaldo. En caso de fallo, se aprovisiona y despliega la infraestructura completa desde cero utilizando plantillas de Infraestructura como Código y se restauran los datos.

    3. RTO/RPO: Altos (horas o días), ya que requiere aprovisionar recursos e ingerir datos tras el desastre. Es la opción más económica.

    4. Pilot Light (Luz piloto):

    5. Funcionamiento: Una versión mínima y esencial de la infraestructura crítica (principalmente la capa de base de datos con replicación activa) se mantiene ejecutándose en la región secundaria. Los servidores de aplicación o cómputo están apagados o en capacidad mínima y solo se despliegan o encienden cuando ocurre un fallo.

    6. RTO/RPO: RTO medio (minutos u horas para escalar la compute), RPO bajo (gracias a la replicación continua de datos).

    7. Warm Standby (Espera en caliente):

    8. Funcionamiento: Una versión reducida pero completamente funcional de toda la pila de aplicación (incluyendo servidores web y de aplicación) se ejecuta de manera continua en la región secundaria, procesando una fracción del tráfico o operando en capacidad baja. Ante una contingencia, la capacidad se amplía rápidamente mediante Amazon EC2 Auto Scaling.

    9. RTO/RPO: RTO bajo (segundos o minutos), RPO muy bajo o cercano a cero.

    10. Multi-Site Active/Active (Multisede activo/activo):

    11. Funcionamiento: La aplicación se ejecuta simultáneamente en dos o más regiones, procesando tráfico de producción en paralelo. Los datos se replican en tiempo real entre ambas regiones.
    12. RTO/RPO: Cercanos a cero (failover casi instantáneo y sin pérdida de datos). Representa la estrategia con mayor coste operativo.

    Amazon Route 53: Políticas de Enrutamiento para Disaster Recovery

    Amazon Route 53 permite gestionar el tráfico global de la aplicación y coordinar las estrategias de conmutación por error (failover) mediante políticas de enrutamiento específicas:

    • Simple Routing: Dirige el tráfico a un único recurso sin comprobaciones de salud (health checks). No es apto para entornos de alta disponibilidad.
    • Failover Routing: Se utiliza para configuraciones Active/Passive (como Pilot Light o Warm Standby). Route 53 evalúa el estado de los recursos mediante health checks. Si el recurso primario falla, Route 53 desvía automáticamente el tráfico hacia el recurso secundario (de respaldo).
    • Latency-based Routing: Enruta las peticiones de los usuarios hacia el endpoint de AWS que ofrezca la latencia de red más baja.
    • Geolocation / Geoproximity Routing: Dirige el tráfico basándose en la ubicación geográfica de los usuarios o mediante restricciones geográficas de cumplimiento normativo.
    • Multivalue Answer Routing: Permite configurar Route 53 para que devuelva hasta ocho registros de recursos saludables elegidos de forma aleatoria en cada consulta, proporcionando un balanceo de carga básico y alta disponibilidad a nivel DNS.

    Seguridad y Automatización de Respuesta a Incidentes

    Amazon GuardDuty

    Servicio de detección de amenazas inteligente y gestionado que monitorea continuamente las cuentas de AWS y las cargas de trabajo en busca de actividad maliciosa o no autorizada. - Fuentes de Datos: Analiza registros de AWS CloudTrail (eventos de API), registros de flujo de Amazon VPC (VPC Flow Logs) y registros de consultas DNS. - Detección basada en Inteligencia Artificial/ML: Identifica comportamientos anómalos, como llamadas a la API desde direcciones IP sospechosas, intentos de desactivar logs o tráfico de red inusual en instancias Amazon EC2.

    AWS Security Hub

    Servicio centralizado de gestión de postura de seguridad que proporciona una vista única de los hallazgos de seguridad (findings) en toda la organización de AWS. - Agregación de Alertas: Recopila y prioriza automáticamente alertas procedentes de servicios nativos de seguridad (como Amazon GuardDuty, Amazon Inspector y Amazon Macie) y de soluciones de terceros integradas. - Estándares de Cumplimiento: Evalúa continuamente la infraestructura frente a marcos de conformidad y estándares industriales (ej. CIS AWS Foundations Benchmark, PCI-DSS).

    Patrón de Automatización de Respuesta a Incidentes (Event-Driven Remediation)

    El diseño operativo estándar para mitigar amenazas de seguridad en tiempo real sin intervención manual combina tres servicios de AWS mediante una arquitectura orientada a eventos: 1. Detección (GuardDuty / Security Hub): Identifica un evento de seguridad crítico (ej. una instancia EC2 comprometida que realiza escaneos de puertos). 2. Enrutamiento (Amazon EventBridge): Captura el hallazgo de seguridad mediante una regla (Rule) configurada con un patrón de eventos específico. 3. Remediación (AWS Lambda): Actúa como destino (Target) de la regla de EventBridge, ejecutando de forma automatizada un script de mitigación (ej. aislar la instancia modificando sus Grupos de Seguridad, revocar claves de IAM comprometidas o tomar snapshots forenses del volumen EBS).
